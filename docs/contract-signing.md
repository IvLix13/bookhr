# Подготовка рапорта и подписание договора

Для договора создаются только два мероприятия: подготовка рапорта и подписание. Срок нового договора выбирается в рапорте (1/2/3/5 лет). Выполнение рапорта сохраняет срок и не меняет текущий договор. Отдельное мероприятие «Подписание договора» назначается на дату окончания текущего договора и создаёт новый договор. До подготовки рапорта подписание недоступно. Рапорт по умолчанию назначается за четыре календарных месяца; переход на ровно 120 дней в этот PR не входит.

Новый период начинается на следующий день после старого окончания. Его окончание считается как начало + выбранное число лет, без вычитания дня. Например, старый договор до 30.11.2026, новый срок 3 года: начало 01.12.2026, окончание 01.12.2029. Для начала 29.02.2028 и срока 1 год окончание — 28.02.2029. Исторические периоды автоматически не пересчитываются. Сохранение без изменения срока и окончания сохраняет исходное начало, включая 29 февраля. При ручном исправлении нового подписанного договора начало фиксируется от предыдущего договора: срок и окончание должны соответствовать этому началу. Сервер отклоняет разрывы и пересечения. Для старых договоров без связи подписания при явном изменении срока или окончания сохраняется прежняя формула начала.

При раннем подписании старый договор остаётся текущим до своего окончания. Новый подписанный период становится текущим с даты начала; чтение работает корректно даже до очередного запуска таймера. Физические флаги активности синхронизирует `run-rules`. Повторные подтверждения не создают ещё один договор; переоткрытие после подписания запрещено.

Подписание подтверждает HR вручную. Оно назначено на последний день старого договора; автоматического подтверждения по дате нет. Подписать можно раньше. При запоздалом подтверждении новый период всё равно начинается на следующий день после окончания старого: это учёт непрерывного периода, а `completed_at` подписания хранит фактическое время подтверждения в приложении.

Автоматическое мероприятие «Договор до…» больше не создаётся. При пересчёте прежние автоматические события окончания, включая выполненные, переводятся в cancelled с комментарием «Мероприятие окончания договора больше не используется». Они исчезают из календаря и перестают отправлять уведомления. История отправок сохраняется до явной очистки отменённых мероприятий. `run-rules` обрабатывает также исторические договоры и уволенных сотрудников; `--company-id` ограничивает выбранную компанию. При редактировании и подписании обрабатываются прежние события соответствующего сотрудника. Ручные мероприятия типа contract не отменяются. После очистки отменённых мероприятий «Договор до…» не восстанавливаются.

Создание договора проверяет компанию и действующее трудоустройство сотрудника и сериализуется блокировкой сотрудника с подписанием и изменением из карточки/импорта. Второй действующий или ожидающий начала подписанный договор через создание запрещён; продолжение оформляется через рапорт и подписание. Убрать договор из подписанной цепочки очисткой полей в карточке нельзя.

При ручном переносе рапорта или автоматическом переносе рапорта/подписания заменяются неотправленные уведомления и эскалации. Отправленная история сохраняется. `run-rules` очищает устаревшие ожидающие уведомления со старой датой; отправщик также отклоняет их, если запускается первым. Для этих исправлений новых миграций и зависимостей нет. Ранее созданные неверные даты и дубли договоров автоматически не исправляются.

## Обновление

1. Обновить backend и frontend из одной версии. Новых зависимостей нет.
2. Выполнить штатную миграцию: `bash scripts/migrate.sh prod` (или `dev` для разработки). Новая ревизия: `0022_contract_signing`, родитель: `0021_onboarding_department`.
3. С тем же окружением и DATABASE_URL из каталога backend выполнить `FLASK_APP=wsgi:app .venv/bin/flask run-rules`. Команда создаст недостающие подписания и связи процессов и отменит все прежние автоматические «Договор до…»; повторный запуск безопасен. Для полного удаления отменённых записей затем можно использовать `scripts/purge-cancelled-events.sh` по инструкции обслуживания.
4. Пересобрать фронтенд (`npm run build`) и перезапустить backend штатным способом.
5. Для чтения диагностики существующих записей: `FLASK_APP=wsgi:app .venv/bin/flask diagnose-contracts`.

Старые выполненные рапорты не доказывают подготовку нового срока: прежняя версия уже могла продлить договор. Их срок автоматически не восстанавливается из текущего договора. Если у актуального старого рапорта нет сохранённого срока, HR явно переоткрывает его и повторно выбирает срок перед подписанием. Исторические даты не исправляются автоматически.

## Проверки реализации

- Исправления договоров, обслуживание и удаление «Договор до…» (04.11.2026): 217 связанных backend-тестов и 36 frontend-тестов проходят. Из backend-набора исключена только подтверждённая на исходном main ошибка `test_confirm_import_creates_three_employment_periods` в импорте стажа. Проверены два мероприятия вместо трёх, отмена старых автоматических событий во всех статусах, область компании, очистка и отсутствие повторного создания, блокировка устаревших уведомлений до пересчёта, импорт, создание сотрудника и пагинация календаря/дня. Проверки выполнены на SQLite; конкурентные транзакции PostgreSQL не проверялись. Новых миграций и зависимостей для этих исправлений нет.
- Полный backend: 443 успешных, 4 ошибки, воспроизводящиеся на исходном main (тесты стажа и старой миграции грейдов). После этого отдельно добавлены и запущены проверки миграции подписания и пограничных дат.
- Связанные frontend-тесты: 46 успешных; typecheck и production build проходят.
- В полном frontend-наборе есть 2 прежние ошибки OnboardingView, подтверждённые на исходном main.
- Миграция подписания проверена на SQLite поверх существующих таблиц, включая downgrade/upgrade и сохранение даты старого договора.
- Конкурентное подписание защищено блокировкой сотрудника и договора в едином порядке и уникальными ограничениями. Исполнение двух соединений на PostgreSQL в этой среде не проверено; его следует выполнить перед рабочим внедрением. SQLite не подтверждает поведение row locks PostgreSQL.
