# Обслуживание договоров и отменённых мероприятий

Оба скрипта запускаются из любого каталога, используют существующий `backend/.venv` и загружают `.env.dev` или `.env.prod` из корня проекта. Ничего из Интернета не устанавливается. Обрабатывается только база, указанная в `DATABASE_URL` выбранного файла, но все компании внутри этой базы. Dev и prod запускаются отдельно.

По умолчанию выполняется только просмотр. `--yes` записывает изменения одной транзакцией; ошибка откатывает операцию. Перед записью сделайте резервную копию и остановите приложение, синхронизацию и таймеры пересчёта/уведомлений на время обслуживания. Сами скрипты службы не останавливают и сообщения не отправляют. Нужны backend этой версии и уже применённая миграция `0022_contract_signing`; новых миграций нет.

## Добавить один день ко всем окончаниям договоров

```bash
bash scripts/extend-contracts-one-day.sh dev
bash scripts/extend-contracts-one-day.sh dev --yes
```

Для рабочей базы замените `dev` на `prod`.

- Меняется только `contracts.end_date`: +1 календарный день у всех записей, включая неактивные, архивные и будущие. Начало, срок, сотрудники и их грейды не меняются.
- Синхронизируется `contract_renewals.source_end_date`. Пересчитываются только правила договоров работающих сотрудников: открытые рапорты и подписания, дата окончания в календаре и ожидающие уведомления. Ручная дата рапорта и выполненные мероприятия сохраняются. Устаревшие открытые события окончания отменяются.
- Предварительный просмотр показывает количество договоров, первые 10 старых/новых окончаний и `linked_periods_start_mismatch_after`: количество связей, у которых сохранённое начало следующего периода не совпадёт с новым окончанием предыдущего +1 день. Так как начала не сдвигаются, при обычной цепочке после массового увеличения может возникнуть совпадение окончания предыдущего с началом следующего. Скрипт выполняет именно увеличение окончаний, а не перестройку цепочек.
- Операция фиксируется в аудите и разрешена один раз для каждой базы. Повторный запуск с `--yes` завершается без нового увеличения. В пустой базе отметка не создаётся. Аудит отдельных договоров сохраняет старое и новое окончание.

## Удалить отменённые мероприятия

```bash
bash scripts/purge-cancelled-events.sh dev
bash scripts/purge-cancelled-events.sh dev --yes
```

Для рабочей базы замените `dev` на `prod`.

Удаляются все `events.status = 'cancelled'`, их строки `event_status_history` и `notification_deliveries` (включая историю отправок этих отменённых мероприятий). Ссылки `report_event_id`/`signing_event_id` в `contract_renewals` предварительно обнуляются. Договоры, выбранные сроки, подписанные результаты, работающие сотрудники, остальные мероприятия и журнал аудита сохраняются. Очистку можно повторять.

Удаление отменённого мероприятия также удаляет факт его отмены из таблицы мероприятий. Если такой рапорт/подписание всё ещё требуется текущему договору, очередной пересчёт создаст его заново. Отменённые события, утратившие актуальность, не возвращаются автоматически. Предпросмотр показывает число удаляемых мероприятий, зависимых строк и затронутых ссылок договоров.

Если нужны оба действия, сначала увеличьте окончания, затем очистите отменённые мероприятия: увеличение может отменить устаревшие события окончания.

## Проверка

Пройдены 16 проверок обслуживания БД и 26 проверок целостности договоров. Проверены предварительный просмотр, однократное увеличение, архивные записи и другие компании, ручные даты, откат после ошибки, очистка при включённых внешних ключах SQLite, повторная очистка и выбор dev/prod оболочками. Синтаксис обоих Bash-скриптов проверен. Конкурентное исполнение на PostgreSQL не проверялось; рабочая база при разработке скриптов не изменялась.
