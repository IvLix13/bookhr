# План реализации модуля «Ошибки в личных документах»

Дата — 11.11.2026. Вариант интерфейса — «Карточки и окно», выбран пользователем для десктопа.

Основа проверки — `IvLix13/bookhr`, ветка `main`, коммит `2c6c0c461233efba15f0824ea50113d33b8b301b`. Список Project Sources пуст. Пути и точки интеграции сверены с исходниками репозитория.

## 1. Сценарий и интерфейс

1. Пользователь с ролью `hr` или `admin` открывает пункт «Ошибки в ЛД» рядом с «Планом ввода в должность» в боковом меню BookHR.
2. На широком экране под заголовком «Ошибки в ЛД» идут полноширинные карточки, по одной на строку. Слева показаны грейд, ФИО и номер ЛД. Справа — красный счётчик ошибок и действие «Открыть ошибки». Использовать общие токены `--surface`, `--bg`, `--border`, `--accent-soft` и стиль карточек онбординга.
3. Нажатие на карточку или действие открывает модальное окно «Ошибки в личных документах». В шапке сведений — ФИО, грейд, номер ЛД и номер карточки. Ниже — таблица из двух столбцов «Вид ошибки» и «Внешнее приложение». В каждой строке есть ссылка «Открыть ЛД ↗».
4. Все ссылки в окне одного сотрудника ведут в его личное дело по адресу `<base_url>/personalfile/<ldnumber>` и открываются в новой вкладке. `ldnumber` передавать как один экранированный сегмент пути с сохранением начальных нулей. Базовый URL задаёт администратор в конфигурации, с явной схемой HTTP или HTTPS и без учётных данных.
5. Для окна переиспользовать оболочку `OnboardingDialog.vue` с обычным режимом до 1000 px, ограничением по высоте экрана, фокусом внутри диалога, закрытием по `Esc` и возвратом фокуса на карточку. Для узких экранов дать метаданным и действиям переноситься на следующую строку.

Рядом со списком показывать время последней успешной загрузки в часовом поясе BookHR. Различать загрузку страницы, успешный пустой снимок («Ошибок не найдено»), отсутствие первого снимка и устаревший снимок после сбоя. Успешный пустой ответ источника заменяет предыдущий список. Исправленные во внешнем приложении ошибки исчезают при следующей успешной синхронизации.

## 2. Контракт источника

Во внешней PostgreSQL БД допускается **один утверждённый `SELECT` на запуск задания**. Исходный текст от пользователя:

```sql
SELECT a.id ,a.ldnumber ,a.cardnumber ,a.grade ,a.f ,a.i ,a.o ,a.datebirth ,b.grade_date_check ,b.post_date_check ,b.contract_date_check ,b.photo_date_check ,b.biography_date_check ,b.attestation_date_check ,b.passport_date_check FROM public.person a inner join public.person_data b on a.ldnumber = b.ldnumber where upper(subdivision) = 'Urah' and dispathed = false and (grade_date_check = false or post_date_check = false or contract_date_check = false or photo_date_check = false or biography_date_check = false or attestation_date_check = false or passport_date_check = false)
```

**Открытый вопрос до первого подключения.** При обычном регистрозависимом сравнении `upper(subdivision)` для `Urah` даёт `URAH`, а литерал в исходном запросе записан как `'Urah'`. Уточнить, какой текст разрешён: исходный или вариант с `= 'URAH'`. Зафиксировать утверждённый текст в коде и проверять его в тесте. Настройку подключения можно подготовить заранее, а первый запуск выполнить после подтверждения запроса.

| Поле ответа | Строка в таблице при `FALSE` |
| --- | --- |
| `grade_date_check` | Ошибка в грейде |
| `post_date_check` | Ошибка в должности |
| `contract_date_check` | Ошибка в договоре |
| `photo_date_check` | Ошибка в фото |
| `biography_date_check` | Ошибка в биографии |
| `attestation_date_check` | Ошибка в аттестации |
| `passport_date_check` | Ошибка в паспорте |

Строку таблицы формировать только при явном `FALSE`. ФИО собирать из `f`, `i`, `o`, пропуская пустые части. `id` — внешний идентификатор. Номера ЛД и карточки хранить строками. `datebirth` входит в утверждаемый запрос, но для выбранного экрана дата рождения не нужна и не попадает в снимок или API.

При повторе строки для одного `ldnumber` и того же внешнего сотрудника объединять коды ошибок без дубликатов. Если один `ldnumber` указывает на разные внешние `id` или отсутствует номер дела, считать результат некорректным и сохранить предыдущий успешный снимок. Сопоставление с `Person`, `Employment`, договорами и другими данными BookHR в этот модуль не входит.

## 3. Синхронизация и локальное API

- Добавить команду `flask sync-personal-document-errors` и отдельные systemd `oneshot`-сервис и таймер по образцу `bookuchet-staff-sync`. Предложенный график — один запуск в сутки, в 06:00 по Москве. При необходимости оператор запускает тот же сервис вручную.
- Использовать отдельное прямое соединение через установленный `psycopg`, отдельную учётную запись только на чтение и конечные таймауты подключения и выполнения. Настраивать таймауты через параметры подключения. Для внешней БД применять режим autocommit, без ORM, `pool_pre_ping`, introspection, проверочного `SELECT 1`, отдельных `SET`, `BEGIN` или SQL при загрузке страницы. Проверить фактические команды на тестовой PostgreSQL БД. При сбое завершать запуск с ошибкой, без автоматических повторов внутри него.
- Хранить один отдельный снимок на разрешённую компанию BookHR в локальной БД. Снимок содержит нормализованный JSON со списком карточек, время последнего успеха и время и результат последней попытки. `PERSONAL_DOCUMENT_ERRORS_COMPANY_ID` явно задаёт, какой компании доступен результат фиксированного внешнего фильтра. Это ограничение доступа к снимку, без связывания записей сотрудников двух систем.
- Защитить задание от параллельных запусков на одну компанию блокировкой в локальном PostgreSQL. Полностью прочитать и проверить результат внешнего запроса до публикации. Заменять снимок целиком атомарно. При таймауте, ошибке чтения или валидации сохранять прошлый список и дату его успеха, отмечать сбой отдельно. В журналы писать время, результат и число карточек без ФИО, номеров дел, строк ответа и DSN.
- Добавить `GET /api/personal-document-errors` по действующему формату `api_response`. Ответ содержит состояние загрузки, `last_success_at` и карточки с полями `external_id`, `ldnumber`, `cardnumber`, `full_name`, `grade`, `errors` и `personal_file_url`. Сортировать по ФИО, при совпадении — по номеру ЛД. Этот GET читает только локальный снимок. Открытие окна использует выбранную карточку из ответа.
- На API применять `require_roles(RoleName.ADMIN, RoleName.HR)` и проверять разрешённую компанию по текущему пользователю через `get_request_company_id()`. На фронтенде использовать `requiresEdit` и `auth.canEdit()` для пункта меню. Данные модуля отдавать с `Cache-Control: no-store`. При выключенной интеграции показывать состояние «Источник не настроен».

## 5. Приёмка

- `hr` и `admin` разрешённой компании открывают вкладку и API. `viewer`, незалогиненный пользователь и пользователь другой компании не получают данные, в том числе при прямом обращении к API.
- Одна карточка соответствует одному личному делу с ошибками. В модальном окне показаны все и только флаги `FALSE`, счётчик совпадает с числом строк, начальные нули в `ldnumber` сохраняются в каждой ссылке.
- Проверены состояния до первой загрузки, с ошибками, после успешной пустой загрузки и после сбоя. Повторяющиеся строки не удваивают счётчик. Повреждённый или частично прочитанный результат не заменяет последний успешный снимок.
- По журналу команд тестового источника успешный запуск выполняет только утверждённый `SELECT`. Веб-запросы, открытие модалки и параллельный запуск при занятой блокировке не обращаются к внешней БД. При сетевом сбое запрос завершается по таймауту, прошлый снимок остаётся доступен.
- В браузере на ширине 1440 и 1920 px проверить сходство с карточками онбординга, открытие и закрытие модального окна, клавиатурную навигацию и переход по каждой строке в нужное личное дело. Проверить также применение миграции и тесты прав, преобразования флагов и атомарной публикации снимка.
