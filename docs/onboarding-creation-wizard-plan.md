# План реализации мастера создания плана ввода в должность

Дата: 28.10.2026.
Статус: пользовательский сценарий и направление дизайна согласованы; реализация не начата.
Репозиторий: `IvLix13/bookhr`, ветка `main`.

## 1. Цель и границы

Заменить создание плана ввода в должность пошаговым мастером для `admin/hr`.
После создания план открывается и ведётся существующим способом. Новая логика завершения обучения, новые статусы сохранённого плана, переработка карточек, Excel и существующего редактора в задачу не входят.

Кнопка «Завершить» в мастере означает **закончить создание и сохранить план**, а не завершить ввод сотрудника в должность.

Текущее состояние проверено непосредственно по исходникам и документации репозитория. Разделы 2–4 фиксируют согласованный сценарий и дизайн; разделы 5–9 описывают технические предложения, ограничения и проверки для реализации.

## 2. Согласованные требования

1. `Admin/hr` открывает раздел плана ввода в должность и нажимает «Создать план».
2. Открывается отдельная view с модальным мастером.
3. Шаги: сотрудник → наставник → мероприятия и плановые даты → сообщение «План подготовлен».
4. На странице предварительной проверки можно исправить даты, заменить наставника и отметить уже выполненные мероприятия.
5. В верхнем правом углу страницы находится меню «бургер»: «Выгрузить план», «Завершить», «Отменить создание».
6. «Завершить» сохраняет план; далее используется существующий интерфейс ведения.
7. «Отменить создание» закрывает мастер без создания плана; при введённых изменениях требуется подтверждение сброса.
8. **Все мероприятия всегда включаются в новый план.** Сейчас их около 50; это рабочий объём, а не константа или ограничение.
9. На шаге мероприятий нужен поиск и прокрутка списка.
10. Сотрудников более 100. Поиск обязателен отдельно при выборе сотрудника и при выборе наставника.
11. Выбран дизайн **«С навигацией»**: шаги слева, содержимое текущего шага справа.
12. Цвета, шрифт, кнопки, поля и скругления мастера должны согласовываться с самим BookHR.

Первоначальное предложение о добавлении и удалении мероприятий уточнено последующим требованием включать все мероприятия: в мастере нет индивидуального отбора, добавления и удаления пунктов. Поиск и фильтры меняют только видимость строк. Настройка общей структуры остаётся в существующем разделе.

## 3. Сценарий пользователя

### 3.1. Открытие

- Заменить текущую точку входа «Добавить сотрудника» на «Создать план».
- Добавить отдельный маршрут создания, например `/onboarding/create`, внутри существующего AppShell с проверкой права редактирования.
- Открыть первый шаг мастера. В настоящем интерфейсе сотрудник и наставник заранее не выбраны, даты не заполняются демонстрационными значениями.
- Данные всех шагов принадлежат одному черновику, живущему до окончательного сохранения или отмены.

### 3.2. Шаг «Сотрудник»

- Поле поиска по ФИО и список результатов под ним. Подразделение может участвовать в поиске и отображении при наличии подходящего источника данных; поиск по ФИО обязателен.
- Строка: ФИО, грейд, доступные сведения о подразделении, дата приёма для различения периодов трудоустройства.
- Выбор одной строки явно выделяется; выбор хранится по идентификатору периода трудоустройства, не по ФИО.
- Смена поисковой строки и страницы результатов не снимает выбранного сотрудника.
- Сотрудника с уже существующим планом для выбранного периода нельзя добавить повторно: показать причину и возможность открыть существующий план.
- Без выбора сотрудника переход дальше сопровождается понятным сообщением.

### 3.3. Шаг «Наставник»

- Тот же паттерн: поиск, список, явное выделение выбранной строки.
- Наставник выбирается из действующих сотрудников текущей компании.
- Показать ФИО и актуальный грейд; отсутствующий грейд обозначать явно, не подставлять вымышленный.
- Не допускать выбора самого сотрудника наставником, в том числе через другой период трудоустройства того же человека.
- При замене сотрудника повторно проверить допустимость наставника. Сохранять прочий ввод, если он остаётся применимым.

### 3.4. Шаг «Мероприятия»

- Загрузить полный актуальный набор неархивных мероприятий компании в порядке настройки.
- Включать все пункты автоматически. Не создавать в коде массив «ровно 50» и не использовать демонстрационные названия из макета.
- Отображать компактными строками: номер, название мероприятия, плановая дата для мероприятий соответствующего типа.
- Названия могут переноситься; поля дат выровнены в отдельном столбце.
- Над списком: поиск мероприятий и переключатель «Без даты».
- Счётчик заполнения относится ко всему плану, например «Даты указаны: 32 из 50». При поиске дополнительно показывать число найденных строк.
- Поиск не удаляет скрытые пункты, не очищает сроки и не изменяет состав плана.
- При незаполненных обязательных сроках «Продолжить» объясняет причину и переводит к незаполненным строкам, сохраняя все значения.
- Для большого списка используем прокрутку внутри списка; заголовок, поиск, навигация слева и нижние кнопки остаются на месте.

**Совместимость с типами текущего модуля:** сейчас есть `stage` — этап с датами, `checkbox` — этап без даты, а также ручные `text` и `date`. Включение всех мероприятий не означает принудительное превращение каждого поля в `stage`. Для `checkbox` календарь не показывается и срок не требуется. Счётчик обязательных плановых дат учитывает только этапы с датами; общее число мероприятий показывается отдельно. Ручные поля сохраняют свой тип и действующее назначение. Нельзя выдавать отсутствие календаря у этапа без даты за ошибку заполнения.

### 3.5. Подтверждение подготовки

После заполнения показать сводку:

> План подготовлен для [грейд] [ФИО]. Наставником является [грейд] [ФИО].

Показать число мероприятий и заполненных сроков. Сообщение относится к подготовке черновика. Формулировку «План создан» показывать только после успешного ответа сервера на окончательное сохранение.

### 3.6. Предварительная проверка на странице

- Закрыть модальную часть мастера и показать подготовленный план на странице создания.
- Дать исправить плановые даты и заменить наставника; возврат в мастер сохраняет ввод.
- Дать отметить выполненные мероприятия. Рядом со статусом отображать «Выполнено», а не использовать placeholder поля даты как единственный индикатор.
- Для этапа с датами отметка выполнения использует существующее правило: фактическая дата по Москве с возможностью исправления. Плановая и фактическая даты не подменяют друг друга.
- Для этапа без даты не создавать скрытые плановые или фактические даты.
- До окончательного сохранения изменения относятся к локальному черновику.

### 3.7. Меню действий

| Действие | Результат |
| --- | --- |
| Выгрузить план | DOCX из текущего черновика, включая последние изменения, без создания плана в БД |
| Завершить | Проверка данных и атомарное создание плана, наставника и начальных ячеек; затем переход к существующему ведению |
| Отменить создание | Подтверждение сброса при наличии ввода и выход без создания плана |

При ошибке выгрузки или сохранения черновик остаётся на экране. Пока сохранение выполняется, повторное нажатие и действия, сбрасывающие ввод, заблокированы.

### 4.2. Компоновка на десктопе

- Сохранить AppShell и навигацию приложения.
- Просторное модальное окно ориентировочно 1000–1100 px, ограниченное доступной шириной и высотой браузера; размеры уточнить при проверке реального интерфейса.
- Левая колонка около 220–240 px: шаги, выбранный сотрудник и наставник.
- Правая часть: заголовок → поиск/фильтр → заголовки столбцов → прокручиваемый список → нижняя панель действий.
- Фиксированы относительно окна мастера: левая колонка, заголовок, поиск и нижние кнопки. Скроллится только список сотрудников или мероприятий.
- Явная видимая полоса прокрутки, без горизонтальной прокрутки основного содержимого на целевых десктопных размерах.
- Проверить 1366×768 и 1920×1080, уменьшенную высоту окна и масштаб браузера 125–150%. Кнопки не должны уходить за нижнюю границу.
- Не переносить в приложение масштабирование всего демонстрационного экрана через `transform: scale`: это приём показа макета в чате, не архитектура интерфейса.

### 4.3. Поведение и доступность

- Один мастер с меняющимся шагом; не накапливать четыре модальных окна друг поверх друга.
- Разрешить возврат на предыдущие шаги без потери выбора, дат и отметок; переход вперёд проверяет обязательные данные предыдущих шагов.
- Поиск, выбор строки, работа с датами и кнопками доступны с клавиатуры.
- Сохранить поведение существующего диалога: управление фокусом, Escape, возврат фокуса, блокировка прокрутки фона и подтверждение сброса ввода.
- Предусмотреть состояния загрузки, пустого результата, ошибки с повтором и конфликта данных.
- Длинные ФИО, названия подразделений и мероприятий переносятся без перекрытия полей.

Важные следствия:

- Нельзя считать ФИО идентификатором сотрудника и создавать план на `person_id`: текущая уникальность относится к периоду трудоустройства.
- Нельзя сохранить пустой план на первом шаге и затем последовательно записывать 50 дат, выдавая это за единую операцию создания.
- Текущая модель куратора — строка `curator_name`, а не ссылка на наставника. Выбор из справочника сам по себе эту модель не меняет.
- Удаление/архивация общей колонки затрагивает планы компании и не является способом убрать пункт только из создаваемого плана.
- Имеющиеся документы описывают исходное поведение. При реализации обновить их, сохранив описание дальнейшего ведения.

## 6. Предлагаемая архитектура реализации

### 6.1. Frontend

1. Добавить `OnboardingCreateView.vue` и защищённый маршрут создания.
2. Разделить оболочку мастера и содержимое шагов; названия новых компонентов уточнить при реализации. Общее поведение диалогов переиспользовать из `OnboardingDialog.vue`.
3. Держать один объект черновика: выбранный период сотрудника, идентификатор наставника, сведения для отображения, полный набор мероприятий с версиями, значения/даты/отметки по постоянным ID, текущий шаг и фильтры.
4. Массив для отображения строить из черновика; результаты поиска не должны становиться источником окончательного payload.
5. Для сотрудников использовать серверный поиск и пагинацию или постепенную подгрузку в прокручиваемую область. Не загружать только первую страницу и не искать исключительно в ней. Игнорировать устаревшие ответы запросов.
6. Для примерно 50 мероприятий достаточно локального поиска по уже загруженному полному набору. Виртуализация на таком объёме не обязательна.
7. Защитить уход со страницы, перезагрузку и закрытие окна при введённых данных. В базовом варианте черновик хранится в памяти: предупреждение предотвращает случайную потерю, но восстановление после закрытия браузера не обещается.
8. Обновить `frontend/src/api/client.ts` и типы под новый контракт. После успешного создания обновить список и открыть сохранённый план существующим способом.

### 6.2. Backend и единое сохранение

Предлагаемый вариант — отдельный сценарий создания из мастера, например `POST /api/onboarding/plans/from-wizard`. Это новый маршрут, а не существующий API. Он не должен менять поведение последующего редактирования ячеек и куратора.

Запрос передаёт:

- `employment_id` сотрудника;
- идентификатор выбранного наставника, а не только введённое на клиенте ФИО;
- полный набор ID и версий структуры, с которым работал пользователь;
- значения начальных ячеек, плановые и фактические даты, отметки выполнения в соответствии с типами.

Сервер в одной транзакции:

1. Проверяет `admin/hr`, текущую компанию, существование периода сотрудника и отсутствие его плана.
2. Проверяет действующего наставника той же компании и запрет наставничества самому себе. ФИО и грейд разрешает из серверных данных.
3. Проверяет полный состав и версии структуры, включая появление новых пунктов. Отклоняет чужие, архивные, повторные и пропущенные обязательные пункты.
4. Проверяет даты и состояния каждого типа. Для этапов с датами требует плановые сроки; для выполненного этапа с датами — корректную фактическую дату; для этапа без даты не создаёт даты.
5. Создаёт план, сохраняет наставника и все начальные значения, записывает аудит.
6. Фиксирует всё вместе и возвращает сохранённый план. Любая ошибка откатывает всю операцию.

Переиспользовать существующие проверки, `lock_company`, транзакционный подход и правила `save_cell`, избегая отдельных commit для каждой ячейки. Версии новых ячеек и аудит должны соответствовать действующей модели.

Для минимального изменения модели наставник при создании записывается в существующий `curator_name` после проверки его идентификатора. Постоянная связь с наставником, автоматическое обновление ФИО/грейда и новая миграция не считаются уже согласованными требованиями. Их необходимость оценить отдельно: текущая DOCX-документация допускает `—` вместо грейда куратора, которого нельзя определить из сохранённой строки. В мастере грейд доступен из выбранного сотрудника; не обещать его автоматическую доступность во всех старых планах.

Существующий короткий контракт создания оценить по вызывающим местам: либо сохранить совместимость, либо явно заменить все его использования. Не отключать старый API без проверки клиентов и тестов.

### 6.3. Выгрузка до сохранения

Предлагаемый маршрут — `POST /api/onboarding/plans/draft-docx` с тем же валидируемым черновиком. Название уточняется при реализации.

- Доступ только `admin/hr` и только в пределах текущей компании, с существующей CSRF-защитой.
- Проверяет идентификаторы, структуру, значения и права; не принимает произвольные сведения другого сотрудника за доверенные.
- Формирует документ из текущего черновика, не создавая временный план и не выполняя записи ячеек в БД.
- Переиспользует действующие DOCX-шаблоны, сопоставления по `document_stage_key`, плановые даты и оформление ответственного отдела.
- Не меняет порядок и состав утверждённого шаблона Word: включение всех мероприятий в план не означает автоматического добавления 50 строк в произвольный шаблон DOCX.
- У существующей выгрузки сохранённого плана остаются действующие правила.

## 7. Риски и обработка ошибок

| Ситуация | Требуемое поведение |
| --- | --- |
| Другой HR создал план того же периода | Серверный конфликт; сохранить ввод, предложить открыть существующий план, не перезаписывать его |
| Структура изменилась во время заполнения | Конфликт состава/версий; обновить структуру с сохранением совместимых значений по ID и повторной проверкой, не сохранять устаревший состав молча |
| Наставник уволен или недоступен к моменту сохранения | Сервер отклоняет назначение; пользователь выбирает другого, сроки остаются |
| Однофамильцы и повторный приём | Выбор по ID и дате приёма; наставничество самому себе проверяется по личности, не по строке ФИО |
| Быстрый ввод в поиск | Старый ответ не заменяет более новый; выбор и введённые даты сохраняются |
| Скрытые поиском незаполненные строки | Глобальная валидация полного черновика, переход к «Без даты», понятное число незаполненных сроков |
| Ошибка на одной из 50 ячеек | Откат всей транзакции, без частичного плана |
| Повторный клик «Завершить» | Блокировка кнопки на клиенте и серверная уникальность периода; не создавать дубль |
| Ответ потерян после отправки сохранения | Не сообщать, что план точно не создан; проверить наличие плана перед повтором, не удалять его через «Отменить создание» |
| Закрытие вкладки до сохранения | Предупреждение о несохранённом вводе; серверного плана до финального запроса нет |
| Не хватает высоты окна | Прокручивается список; поиск, шаги и кнопки доступны без прокрутки страницы целиком |
| Неверное состояние или даты в подменённом запросе | Серверная валидация независимо от проверок интерфейса |
| Недоступен DOCX-шаблон или сбой выгрузки | Понятная ошибка без потери черновика и без скрытого сохранения |

## 8. Порядок работ

1. Проверить актуальные исходники перед началом реализации, уточнить состав настроенных мероприятий и источники данных сотрудников.
2. Описать DTO черновика, правила типов полей, поиск сотрудников/наставников и контракт атомарного создания. Подготовить backend-проверки.
3. Реализовать серверное создание и выгрузку черновика с повторным использованием существующих механизмов.
4. Реализовать view и оболочку «С навигацией» на общих стилях приложения.
5. Реализовать выбор сотрудника и наставника с поиском, устойчивым выбором и корректной работой при 100+ сотрудниках.
6. Реализовать полный список мероприятий, прокрутку, поиск, «Без даты», глобальные счётчики и сохранение ввода между шагами.
7. Реализовать сообщение «План подготовлен», предварительную проверку, отметки выполнения, замену наставника и меню действий.
8. Подключить атомарное сохранение, отмену, защиту несохранённых данных, ошибки и конфликты. После успеха перейти к действующему ведению плана.
9. Обновить документацию использования и развёртывания, выполнить проверки и визуальную приёмку.

Новые runtime-зависимости не добавлять без необходимости: проект используется в офлайн-контуре. Потребность в миграции определяется финальной моделью, а не внешним видом мастера; серверные черновики для описанного базового варианта не требуются.

## 9. Критерии приёмки и проверки

### Сценарий и масштаб

- [ ] Создание доступно только `admin/hr`; прямой переход viewer на маршрут и вызов API не дают права создать план.
- [ ] Новый план создаётся только после «Завершить»; отмена до отправки запроса не оставляет план и ячейки.
- [ ] Сотрудник и наставник выбираются через поиск; проверены 120+ тестовых сотрудников, однофамильцы, несколько периодов и устаревшие ответы.
- [ ] Все настроенные мероприятия включены. Поиск и «Без даты» не меняют состав запроса.
- [ ] Проверены 50+ мероприятий, длинные названия, пустая выдача и поиск, скрывающий незаполненные строки.
- [ ] Даты и выбор сохраняются после поиска, возврата между шагами и исправления ошибки.
- [ ] Этапы без даты не требуют дат; ручные поля не превращаются в мероприятия с обязательным сроком.
- [ ] Глобальный счётчик отражает весь план и только подходящие по типу поля.
- [ ] Сотрудник и наставник показаны с ФИО и доступным грейдом; отсутствию грейда соответствует явная подпись.
- [ ] Выполнение и фактические даты сохраняются по существующим правилам, включая московскую дату.
- [ ] Выгрузка до сохранения содержит текущие данные и не создаёт план в БД.
- [ ] Сбой выгрузки/сохранения оставляет ввод доступным для исправления и повтора.

### Целостность и совместимость

- [ ] Создание атомарно: ошибка последней ячейки не оставляет частично созданный план.
- [ ] Проверены конфликт существующего плана, изменение структуры, недействительный наставник, чужая компания и двойной запрос.
- [ ] Уникальность плана по периоду трудоустройства сохранена; новый период допускает новый план.
- [ ] Проверена неопределённость результата при потере ответа после сохранения.
- [ ] После создания работают существующие карточки, сортировка по времени создания, редактор ячеек, куратор, статусы, удаление и выгрузки.
- [ ] Существующие планы не требуют повторного прохождения мастера.

### Визуальная и техническая приёмка

- [ ] Используются общие CSS-переменные BookHR, без отдельной зелёной/фиолетовой темы мастера.
- [ ] На целевых десктопных разрешениях и при масштабе 125–150% кнопки, поиск и навигация остаются видимыми; прокручивается список.
- [ ] Проверены клавиатура, фокус, Escape, подтверждение отмены, отсутствие фоновой прокрутки и доступность сообщений об ошибках.
- [ ] Backend: целевые тесты создания/валидации/транзакций/DOCX и существующие проверки онбординга.
- [ ] Frontend: целевые тесты маршрута, шагов, поиска, сохранности ввода и полного payload; `npm run typecheck`, `npm test`, `npm run build`.
- [ ] Обновлены `docs/onboarding.md` и `docs/onboarding-docx.md` по фактической реализации.
