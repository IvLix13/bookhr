## Требования

1. Открывать план сотрудника в модальном окне вместо раскрытия карточки на странице.
2. Разрешить удаление этапов и ручных полей в настройке структуры.
3. Добавлять сотрудника в план через модальное окно.
4. Добавить удаление планов и сотрудников вместе с их планами.
5. По умолчанию показывать сначала сотрудников с недавно созданным планом ввода, затем с более ранним (уточнение требования от 11.10.2026).

Фото и телефон остаются вне объёма работ. Расчёт прогресса, состояния этапов, куратор, поиск, экспорт и существующие права редактирования сохраняются.

## Проверенное состояние

- `OnboardingView.vue` раскрывает карточки через `expanded: Set<number>`; выбор сотрудника встроен в страницу.
- `OnboardingPlanCard.vue` содержит сводку, детали и редактирование куратора.
- Настройка структуры уже находится в `OnboardingColumnsModal.vue`. `OnboardingColumns.vue` поддерживает архивирование и восстановление, но не удаление.
- API выдаёт планы по возрастанию `OnboardingPlan.id`, затем применяет пагинацию. После добавления UI переходит на последнюю страницу.
- План связан с периодом трудоустройства (`employment_id`), а не со всеми периодами одного человека.
- API удаления сотрудника уже существует: `DELETE /api/employees/<employment_id>`. Сервис `delete_employment` запрещает удалять сотрудника, имеющего план обучения.
- У связей ячеек с планом и полем нет настроенного удаления дочерних записей. Нельзя просто удалить родителя и рассчитывать на каскад.

## План в модальном окне

- Карточка в списке показывает сводку и кнопку «Открыть план». Убрать встроенную таблицу и набор раскрытых карточек.
- Добавить `OnboardingPlanModal.vue`: ФИО, грейд, дата прихода, отдел, куратор, прогресс и таблица активных этапов/полей.
- При открытии получать актуальный план через существующий GET `/api/onboarding/plans/<id>`. Показывать загрузку, ошибку и повтор запроса внутри окна.
- Сохранять существующий редактор ячейки. После сохранения обновлять открытый план и сводку в списке, не закрывая окно и не сбрасывая его прокрутку без необходимости.
- HR/admin меняют куратора и управляют удалением; viewer редактирует только разрешённые ему ячейки по действующим правилам совпадения ФИО.
- Поддержать диалог с заголовком, Escape, крестиком, возвратом фокуса и блокировкой прокрутки фона. Клик по фону не закрывает окно с вводом.
- При несохранённом вводе запрашивать подтверждение сброса; во время сохранения блокировать закрытие и повторную отправку.
- Для вложенного редактора/подтверждения активен только верхний focus trap. После его закрытия фокус возвращается в окно плана; прокрутка страницы остаётся заблокированной до закрытия последнего окна.
- На телефоне окно помещается в viewport, длинные значения переносятся, содержимое прокручивается.

## Добавление сотрудника через модальное окно

- Выделить `OnboardingAddEmployeeModal.vue`, используя существующий поиск сотрудников и POST `/api/onboarding/plans`.
- Кнопка «Добавить сотрудника» открывает диалог с поиском, результатами, датой приёма и пагинацией; встроенный `add-panel` убрать.
- Сохранять отображение отдельных периодов трудоустройства и статуса «уволен». Существующий план для периода повторно не создаётся; ответ 409 показать в диалоге.
- Блокировать повторное создание, пока запрос выполняется. Ошибка сохраняет поисковый запрос и результаты.
- Игнорировать ответы устаревших запросов поиска и ответы после закрытия окна.
- После успеха закрыть окно, обновить список и открыть созданный план по возвращённому ID. Отменить старый переход на последнюю страницу: место карточки определяется временем создания плана.
- При создании сбросить поиск списка и перейти на первую страницу. Новый план появляется первым независимо от даты приёма сотрудника; после создания он также доступен в открытом диалоге.

## Удаление этапов и полей

- В настройке добавить отдельную кнопку «Удалить» для всех ручных типов: `stage`, `checkbox`, `text`, `date`, включая архивные поля. Системные сведения сотрудника удалять здесь нельзя.
- Архивирование сохранить как самостоятельную операцию.
- Перед удалением показать название поля и пояснение: поле и его значения будут удалены у всех сотрудников компании; восстановление через кнопку архива невозможно.
- Ввести DELETE `/api/onboarding/columns/<id>` с обязательной ожидаемой `version` в JSON-теле, доступный HR/admin.
- Выполнить в одной транзакции под существующей блокировкой компании: проверить компанию и версию, записать аудит, удалить связанные ячейки, затем поле. Не затронуть структуру других компаний.
- Заполненные поля также можно удалить после явного подтверждения. Предусмотреть актуальную сводку числа затронутых ячеек в подтверждении; при изменении данных с момента подтверждения вернуть 409 и потребовать повторного подтверждения, а не удалять незаметно новые значения.
- Снимок для проверки актуальности включает версии затронутых ячеек: одна версия поля не меняется при редактировании значения. Не заменять эту проверку только числом ячеек.
- В аудит включить название, тип, версию поля и удалённые значения с идентификаторами планов; не считать аудит пользовательским механизмом восстановления.
- После успеха обновить структуру, открытый план и прогресс карточек; сбросить форму, если редактировалось удалённое поле. На ошибке сохранить окно и ввод.
- Старый редактор удалённого поля получает понятную ошибку и не создаёт поле или ячейку заново.

## Удаление плана и сотрудника

Предусмотреть две разные операции в окне плана:

| Действие | Результат |
| --- | --- |
| Удалить план | Удалены план, куратор и все его ячейки; сотрудник и период трудоустройства сохранены. Позже можно создать новый пустой план. |
| Удалить сотрудника и план | Удалены выбранный период трудоустройства, его план и данные, которые уже удаляет `delete_employment`. Другие периоды трудоустройства человека сохраняются. Запись человека удаляется только при отсутствии всех его периодов, по текущему правилу сервиса. |

- В подтверждении показывать ФИО и дату приёма, чтобы различать периоды. Для удаления сотрудника дополнительно перечислить связанные данные: события/доставки, договоры, историю грейдов и должностей, награды; объяснить необратимость операции.
- Удаление плана: новый DELETE `/api/onboarding/plans/<id>` с обязательной ожидаемой версией и проверкой актуального снимка ячеек.
- Удаление сотрудника с планом: расширить существующий DELETE `/api/employees/<employment_id>` явным флагом `delete_onboarding_plan=true` и ожидаемым снимком плана/ячеек. Без флага сохранить нынешний запрет при наличии плана, чтобы прежние клиенты не удаляли его неявно.
- Обе операции доступны HR/admin и ограничены текущей компанией. Viewer не видит кнопок и получает 403 при прямом запросе.
- В сервисе выделить общее удаление плана с ячейками и аудитом; использовать его из обоих маршрутов без промежуточного commit.
- Удаление сотрудника, плана и связанных данных выполняется атомарно. Ошибка откатывает всю операцию.
- Удаление сотрудника должно использовать ту же блокировку компании, что создание/изменение onboarding, чтобы не возникала гонка с созданием плана или сохранением ячейки.
- Снимок и версии проверяются под блокировкой непосредственно перед удалением. После конфликтов обновить данные и запросить новое подтверждение.
- После успеха закрыть окно удалённого плана, обновить список и счётчик. Если последняя карточка страницы удалена, перейти на последнюю доступную страницу. Не терять текущий поиск.

## Сортировка по времени создания плана

- Уточнённое правило: сначала идут недавно созданные планы; дата приёма сотрудника не влияет на порядок.
- В API списка применить `OnboardingPlan.created_at DESC`, затем `OnboardingPlan.id DESC` для стабильного порядка при одинаковом времени создания, до OFFSET/LIMIT.
- Сортировка действует при поиске, на границах страниц и в Excel-экспорте, без изменения набора столбцов.
- Редактирование куратора, этапов, дат или сведений сотрудника не поднимает план в списке. При удалении и создании нового плана используется новое время создания.
- Не сортировать только текущую страницу на frontend; не менять глобальную сортировку справочника сотрудников.

## Результат реализации

В `feat/onboarding-cards` реализованы модальные окна плана и добавления сотрудника, удаление поля/плана/периода трудоустройства вместе с планом, серверная сортировка по `plan.created_at DESC, plan.id DESC` и такой же порядок Excel. Общие оболочка диалога, подтверждение удаления и блокировка прокрутки вынесены в `OnboardingDialog.vue`, `OnboardingDeleteDialog.vue`, `useBodyScrollLock.ts`; детали плана — в `OnboardingPlanDetails.vue`. Проверки новых окон объединены в `OnboardingModals.test.ts`.

Удаление проверяет `version` и SHA-256 снимка текущих данных из GET `delete-preview`, включая версии/значения ячеек. Удаление сотрудника использует существующий маршрут с явным флагом `delete_onboarding_plan: true`; без флага прежний запрет сохраняется. Дочерние записи удаляются сервисами, новая миграция не нужна.

Проверены typecheck, все 202 frontend-теста (42 файла), production build, 82 backend-теста onboarding и CRUD сотрудников. Проверены сценарии в Chromium на ширинах 1440 и 390 px с тестовыми ответами API: план, куратор, редактор этапа, добавление, удаление плана и поля, вложенные окна и прокрутка; ошибок JavaScript нет. Проверки транзакций и удаления данных выполняются серверными тестами.

Полный backend-прогон: 378 пройденных тестов и 4 прежних падения: `test_tenure_list_sort_by_tenure_years`, `test_grade_policy_migration_upgrade_backfill_and_downgrade`, `test_confirm_import_creates_three_employment_periods`, `test_run_rules_creates_award_events_visible_in_api`. Эти падения были подтверждены на исходной версии до текущей доработки. Дополнительно проверены удаление сотрудника с зависимостями, возврат фокуса при одновременном закрытии окон и пагинация после удаления последней карточки. При удалении родительских записей сбрасываются загруженные ORM-коллекции после удаления дочерних строк, чтобы исключить ошибку внешнего ключа при удалении сотрудника после просмотра плана.

Для установки обновить backend и пересобранный frontend вместе. Если карточки ещё не устанавливались, предварительно применить существующую миграцию `0019_onboarding_cards`. Новых зависимостей нет.
