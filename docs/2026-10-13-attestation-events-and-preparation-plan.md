## 1. Требования клиента и принятая трактовка

1. Для сотрудника с заданной датой аттестации автоматически формировать два связанных события:
   - «Подготовка документов для аттестации»;
   - «Проведение аттестации».
2. Дата подготовки документов = дата проведения аттестации − 14 календарных дней.
3. Изменение даты или факта проведения аттестации из раздела «Все мероприятия» либо модуля «Аттестация» должно синхронизировать данные и повторно рассчитывать дату подготовки.
4. В таблице модуля «Аттестация» добавить колонку «Дата подготовки документов».

Формулировку клиента «2 недели − даты проведения» понимаем как **за две недели до проведения**, а не наоборот. Выходные и праздники не сдвигают результат.

Пример: проведение 30.10.2026 → подготовка 16.10.2026; перенос проведения на 06.11.2026 → подготовка 23.10.2026.

Факт проведения — статус `completed` события «Проведение аттестации». В модуле «Аттестация» дать возможность выполнить/переоткрыть это же событие через существующую карточку мероприятия. Отдельный независимый флаг в БД не вводить.

При изменении только факта проведения формула применяется повторно, но результат остаётся прежним, если дата не менялась. `completed_at` — время регистрации выполнения, а не замена даты проведения. Если HR корректирует дату реально проведённой аттестации, обе даты обновляются, статус выполнения и история сохраняются.

Новая периодичность аттестации, автоматическое назначение следующей аттестации, изменение грейда и автоматическое выполнение подготовки клиентом не запрошены. Не добавлять их.

## 3. Данные и идентификация событий

1. Сохранить `Employment.attestation_date` единственным хранимым источником даты проведения.
2. В новом сервисе `backend/app/services/attestations.py` определить:
   - константу срока подготовки 14 дней;
   - чистую функцию расчёта даты через `timedelta(days=14)`;
   - поиск пары связанных событий с обязательным ограничением по компании и сотруднику;
   - изменение даты с синхронизацией пары и аудитом;
   - обработку изменения факта проведения.
3. Добавить два явных EventType:
   - `attestation_preparation` — подготовка документов;
   - `attestation` — проведение аттестации.
4. Оба события имеют `source=rule`, `employment_id`, `company_id`, `reference_type="employment"`, `reference_id=employment.id`.
5. Для текущей аттестации использовать стабильные ключи без даты:
   - `attestation-preparation:{company_id}:{employment_id}`;
   - `attestation-conduct:{company_id}:{employment_id}`.
6. Перенос даты обновляет те же записи и сохраняет их ID, историю статусов и связи. Повторный пересчёт не создаёт дубликатов.
7. Для аттестации не использовать `manual_date` как независимое переопределение: дата проведения меняет источник `Employment.attestation_date`, подготовка всегда вычисляется от него.
8. Дата подготовки в ответе API вычисляется той же функцией и не хранится отдельной колонкой БД.
9. Это модель текущей аттестации сотрудника. Несколько параллельных планов или отдельный архив периодических циклов потребуют отдельной задачи; не создавать новые циклы при обычной корректировке даты.

## 4. Пересчёт и жизненный цикл

### 4.1. Установка и перенос даты

- При первой установке даты создать пару событий с названиями и ФИО сотрудника.
- При переносе обновить дату проведения и дату подготовки в одной транзакции.
- Не ограничивать прошедшую дату подготовки сегодняшним днём: сохранять точный результат «минус 14 дней».
- Для открытых событий пересчитывать статус: прошедшая дата → просрочено, дата сегодня/в будущем → запланировано. Использовать существующие функции переходов статусов и московскую дату.
- Повторное сохранение той же даты не добавляет события и записи истории без изменения данных.

### 4.2. Изменение факта проведения

- Выполнение проведения меняет статус этого события на `completed`; пересчёт не создаёт новое открытое проведение.
- Переоткрытие снимает факт выполнения через существующий переход статуса и повторяет расчёт дат.
- Переоткрытие аттестации сохраняет заданную дату; не переносить её автоматически на сегодня.
- Выполнение подготовки меняет только статус подготовки. Оно не означает проведение аттестации.
- Выполнение проведения не отмечает подготовку выполненной автоматически.
- Отдельно разрешить исправление даты завершённого проведения. Обновить обе расчётные даты, сохранив статус, `completed_at`, автора выполнения и историю; исправление даты записать в аудит.
- При исправлении даты обновлять дату подготовки даже у уже завершённой подготовки. Её факт выполнения и время регистрации выполнения сохраняются.
- Не блокировать проведение из-за невыполненной подготовки: такого ограничения клиент не указал.
- Все эффекты аттестации определять по типу и связи события, а не по тексту заголовка.

### 4.3. Очистка даты, отмена и отсутствие активного сотрудника

- Для сотрудника без даты ответ API содержит обе даты `null`; новые события не создаются.
- При очистке даты отменить связанные открытые события через существующие переходы статусов, сохранив историю. Завершённые записи не удалять и не стирать.
- После очистки даты карточка текущей аттестации не должна предлагать выполнение/переоткрытие исторической записи без повторного задания даты.
- При повторном задании даты восстановить открытые записи, отменённые именно вследствие очистки даты, с новым расчётом; различать техническую и явную пользовательскую отмену.
- Корректировка существующей завершённой записи не снимает выполнение. Новый факт проведения требует явного переоткрытия, а не простого изменения даты.
- Явная отмена пользователем сохраняется при фоновом пересчёте: не воссоздавать отменённое событие автоматически. Возврат — через явное переоткрытие.
- Для неактивного сотрудника новые события не формировать, открытые отменять по принятому механизму rule engine; историю завершённых сохранять.
- Мутации связанного события неактивного сотрудника отклонять, чтобы оно не было переоткрыто и тут же отменено пересчётом.
- Если требуемая дата слишком ранняя для вычитания 14 дней, возвращать понятную ошибку валидации, не 500.

### Очередь существующих уведомлений

Если для аттестации действуют включённые правила уведомлений:

- при переносе даты пересчитать ожидающие доставки для новой даты;
- старые неотправленные доставки не должны отправляться по прежнему расписанию или дублировать новые;
- обработать как `pending`, так и ожидающие повторной попытки `failed`;
- не удалять журнал уже отправленных сообщений и не отправлять их повторно без основания;
- после выполнения/отмены не отправлять ожидающие уведомления закрытого события;
- проверки выполнять с подменённой отправкой, без реальных сообщений.

Использовать текущий механизм уведомлений, не добавлять новые каналы или правила по умолчанию.

`Employment.attestation_date` и общие правила отображения календаря сохраняются; изменение `employee.py` и `CalendarView.vue` не требуется для базового решения.

## 9. Данные, выпуск и приёмка

Миграция схемы БД для выбранного решения **не нужна**: дата проведения уже есть, дата подготовки вычисляется, факт хранится существующим статусом Event, типы событий хранятся строками.

После реализации обновить backend/frontend совместно и выполнить штатную команду `flask run-rules --company-id <id>` в нужном окружении для создания событий по уже заданным датам аттестации. Команда затрагивает и существующие правила компании, поэтому до её выполнения проверить регрессионные тесты и использовать штатный порядок обновления с резервной копией БД. Автоматическое создание событий через GET не добавлять. Факты проведения старых записей не угадывать: существующая дата сама по себе не означает выполнение.

Приёмка: есть два связанных события, подготовка всегда датирована за 14 календарных дней до проведения, оба пути редактирования и изменения факта согласованы, завершённые записи и история сохраняются, дубликаты отсутствуют, новая колонка отображается и сортируется, права и изоляция компаний соблюдены.

В рамках текущей задачи создаётся и публикуется **только этот план**. Код приложения и данные БД не изменять.
