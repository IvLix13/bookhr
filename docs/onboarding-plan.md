# План реализации: ввод сотрудника в должность

Дата: 19.09.2026.
Статус: реализован по подтверждённым ниже правилам. Инструкция: [onboarding.md](onboarding.md).

## Подтверждение перед реализацией

Пользователь подтвердил следующие решения, которые имеют приоритет над открытыми вопросами первоначального плана ниже:

1. Грейд — текущий фактический; ФИО актуальное; номер — порядковый в списке.
2. HR/admin вручную выбирают существующего сотрудника без ограничения intern. Один план на период трудоустройства.
3. Отдел и дата начала — ручные поля плана, не меняющие карточку сотрудника.
4. При выполнении подставляется сегодняшняя дата по Москве с возможностью исправления. Предварительный срок необязателен. При отмене выполнения текущая дата выполнения очищается, срок и аудит сохраняются.
5. Viewer читает; HR/admin меняют структуру и значения. Набор столбцов общий для компании.
6. Увольнение сохраняет план. Удаление сотрудника с планом запрещено, в том числе через массовую очистку.
7. Календарь, уведомления и Excel не входят в реализацию.

Ниже сохранён исходный проектный план; раздел 11 отражает вопросы на момент его составления, уже разрешённые этим подтверждением.

## 1. Цель и подтверждённые требования

Создать таблицу планов обучения сотрудников для ввода в должность.

- Исходная таблица предполагает 25 столбцов, но это не ограничение модели.
- Первые три столбца: Номер, Грейд, ФИО. Их значения формируются автоматически.
- Все остальные значения HR или admin вводят самостоятельно.
- HR и admin могут изменять структуру таблицы через интерфейс, а не только значения ячеек.
- Этап отображается как дата, к которой его нужно выполнить; после выполнения — зелёная галочка и дата.
- Дату и состояние «выполнено / не выполнено» можно исправлять, в том числе возвращать этап в невыполненное состояние.
- Полный список столбцов заранее не требуется для разработки гибкой основы. Его можно сформировать через интерфейс.
- Текущая задача — сохранить план. Код приложения, БД и рабочие данные не изменять до отдельного поручения.

## 2. Предлагаемые правила (основа реализации, не отдельные подтверждения клиента)

Следующие детали предложены в обсуждении; открытые бизнес-вопросы перечислены в разделе 11.

### Структура таблицы

- Одна строка — план конкретного сотрудника.
- Системные столбцы Номер, Грейд, ФИО нельзя удалить или превратить в пользовательские поля.
- Пользовательские столбцы можно добавлять, переименовывать, переставлять, архивировать и восстанавливать.
- Определения столбцов общие для всех строк таблицы в пределах текущей компании.
- Новый столбец появляется у всех сотрудников с пустыми значениями; массовое создание пустых ячеек в БД не требуется.
- Переименование и изменение порядка не меняют идентификатор столбца и не теряют значения.
- Архивирование скрывает столбец, но сохраняет значения. Безвозвратное удаление заполненных столбцов в первую версию не включать.
- Изменение типа заполненного столбца запрещено на сервере. Архивные значения также считаются данными.

### Типы пользовательских столбцов

| Тип | Данные | Пример |
| --- | --- | --- |
| Текст | Строковое значение | Отдел |
| Дата | Календарная дата без статуса | Дата начала |
| Этап | Плановая дата, состояние, дата выполнения | Пропуск, NDA, экзамен, план обучения |

Название «План обучения» в столбце пока трактуется как этап, а не загрузка файла.
Не добавлять хранение вложений без отдельного согласования.

### Состояния этапа

| Состояние | Отображение |
| --- | --- |
| Данные не заполнены | Прочерк |
| Не выполнено, срок задан | Плановая дата |
| Выполнено | Зелёная галочка и дата выполнения |
| Не выполнено, срок прошёл | Плановая дата с выделением просрочки — предлагаемое улучшение |

Плановую дату и дату выполнения хранить отдельно: выполнение не должно уничтожать первоначальный срок.
Просрочка вычисляется по сроку и состоянию, а не хранится третьим ручным статусом.

Предлагаемое правило отмены выполнения: сохранить плановую дату, очистить текущую дату выполнения, прежнее значение оставить в аудите.
Способ подстановки даты выполнения требует согласования: сегодняшняя дата с возможностью исправить либо обязательный ручной выбор.
Редактирование через небольшую форму ячейки с явными действиями «Сохранить» и «Отмена».

## 4. Модель данных

Не добавлять по отдельному полю в Employment для каждого этапа. Не создавать SQL-столбцы через интерфейс.

### OnboardingColumn — определение пользовательского столбца

Предлагаемые поля:

- id — стабильный идентификатор;
- company_id — область доступности;
- title — название;
- field_type — text / date / stage;
- sort_order — порядок;
- is_archived — признак архива;
- created_at, updated_at; сведения об авторе изменений через принятый механизм аудита.

Системные столбцы можно определить в коде отдельно; API не должен позволять изменять их как пользовательские.

### OnboardingPlan — строка плана

- id;
- employment_id — ссылка на конкретный период трудоустройства;
- company_id либо однозначное определение компании через Employment;
- created_at, updated_at.

Связь с employment_id отделяет планы при повторном приёме одного человека.
Ограничение числа планов на трудоустройство определить после ответа на вопрос об однократных/повторных планах.
Номер строки не использовать как ключ связи.

### OnboardingCell — значение ячейки

- id;
- plan_id;
- column_id;
- text_value — для текста;
- date_value — для обычной даты;
- planned_date, is_completed, completed_date — для этапа;
- created_at, updated_at.

Ограничение уникальности: одна ячейка на пару plan_id + column_id.
Поля, не соответствующие типу столбца, должны оставаться пустыми.
Отсутствующая запись означает пустую ячейку, а не ошибку.

ФИО и выбранный грейд получать из существующих связей сотрудника, не дублировать вручную.
Решение о текущем грейде либо снимке на начало плана зафиксировать до реализации.

### Целостность и сохранение данных

- Проверять принадлежность плана, столбца и сотрудника одной компании.
- При архивировании столбца не удалять ячейки.
- Переупорядочивание выполнять атомарно.
- Предусмотреть защиту от незаметного перезаписывания параллельных правок через версию/updated_at и сообщение о конфликте.
- До миграции согласовать поведение при удалении и увольнении сотрудника; не добавлять случайное каскадное удаление.
- Аудит должен фиксировать старое и новое значение, пользователя и время для изменений ячеек и структуры.

Предлагаемые операции API:

- GET /onboarding/columns — структура;
- POST /onboarding/columns — новый столбец;
- PATCH /onboarding/columns/:id — название, допустимое изменение типа, архивирование/восстановление;
- PATCH /onboarding/columns/order — порядок столбцов;
- GET /onboarding/plans — строки с пагинацией;
- POST /onboarding/plans — создание строки для существующего сотрудника;
- GET /onboarding/plans/:id — план;
- PATCH /onboarding/plans/:id/cells/:column_id — изменение ячейки.

Окончательные пути согласовать с текущим префиксом /api и соглашениями проекта.
Не вводить дополнительные операции удаления без определённых правил.

Валидация:

- непустое название и допустимый тип столбца;
- корректные календарные даты;
- согласованность статуса и даты выполнения;
- соответствие значения типу;
- запрет записи в системные и архивные столбцы;
- запрет смены типа при наличии данных;
- запрет доступа к данным чужой компании;
- проверка сотрудника при создании плана;
- отсутствие возможности менять структуру через обычное обновление ячейки.

Строки и ячейки загружать пакетно, без отдельного запроса для каждой ячейки.
Изменение одной ячейки не должно отправлять и перезаписывать всю таблицу.

## 6. Frontend

### Основной экран «План обучения»

Предлагается отдельный пункт меню и маршрут:

- горизонтальная прокрутка для широкой таблицы;
- закреплённые слева Номер, Грейд, ФИО;
- пользовательские столбцы в заданном порядке;
- пагинация и поиск по ФИО по существующим соглашениям;
- состояния загрузки, пустой таблицы, ошибки и повторной загрузки;
- добавление сотрудника через выбор из существующих записей;
- автоматическое отображение ФИО и грейда;
- редактирование текста, даты или этапа соответствующей формой.

Фильтры по грейду/состоянию плана — дополнительное предложение, не обязательное согласованное требование.
Не рассчитывать общий статус плана, пока не определено, какие этапы обязательны.

### Управление структурой

Кнопка «Настроить столбцы» доступна HR/admin:

- список столбцов с типами;
- добавление с названием и выбором типа;
- переименование;
- изменение порядка;
- архивирование с предупреждением о скрытии столбца для всех строк;
- просмотр архива и восстановление;
- объяснение запрета смены типа при заполненных ячейках.

Изменение структуры отражается во всей таблице текущей компании.
При конфликте с другой сессией обновить структуру и предложить повторить действие, не теряя ввод молча.

### Права

| Действие | admin | hr | viewer |
| --- | --- | --- | --- |
| Просмотр | Да | Да | Предлагается разрешить |
| Создание плана и изменение ячеек | Да | Да | Нет |
| Управление структурой | Да | Да | Нет |

Просмотр viewer отдельно подтвердить.
Ограничения реализовать на сервере, а не только скрытием кнопок.

## 10. Не включать автоматически

Без отдельного согласования не добавлять:

- события обучения в календарь и «Требует внимания»;
- уведомления;
- импорт/экспорт Excel;
- файловые вложения;
- автоматический расчёт сроков;
- разные шаблоны по грейдам/отделам;
- обязательность этапов и расчёт процента/статуса всего плана;
- конструктор произвольных формул;
- автоматическое включение всех сотрудников;
- изменение основной карточки сотрудника ради поля отдела.

Это сохраняет границы первоначального запроса.

## 11. Открытые вопросы перед реализацией
