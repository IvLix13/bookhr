# Выгрузка плана ввода в должность (DOCX)

В окне плана сотрудника нажмите **Выгрузить план**. Выгружаются сохранённые данные;
незавершённое редактирование необходимо сохранить или отменить.

В документ попадают актуальная должность, фактический грейд и Фамилия И.О.
сотрудника и Фамилия И.О. куратора (из текстового поля плана). Переменная
`curator_grade` в этой ветке остаётся `—`, если грейд нельзя определить.
Для этапов берётся
**плановый срок**, даже если этап уже выполнен. Фактическая дата не используется.
Отсутствующий, архивный, несопоставленный этап, пустая дата и состояние «Не нужно»
дают `—`. Строки документа при этом сохраняются.

## Словарь переменных

`backend/app/templates/onboarding/variables.json` — словарь
`"имя переменной шаблона": "источник данных приложения"`.
В Word вставляйте переменные с двойными фигурными скобками:

| Переменная в Word | Значение |
| --- | --- |
| `{{ employee_name }}` | Фамилия И.О. сотрудника |
| `{{ employee_full_name }}` | Полное ФИО сотрудника |
| `{{ employee_position }}` | Актуальная должность |
| `{{ employee_grade }}` | Фактический грейд |
| `{{ curator_name }}` | Фамилия И.О. куратора |
| `{{ curator_full_name }}` | Полное ФИО куратора |
| `{{ curator_grade }}` | Фактический грейд куратора |
| `{{ pass_planned_date }}` | Пропуск: плановая дата |
| `{{ nda_planned_date }}` | NDA: плановая дата |
| `{{ competence_exam_planned_date }}` | Экзамен на компетентность: плановая дата |
| `{{ training_plan_planned_date }}` | План обучения: плановая дата |

Даты имеют формат `ДД.ММ.ГГГГ`. Переменные работают в абзацах, таблицах и
колонтитулах, в том числе если Word разделил переменную на несколько фрагментов.
Условий, циклов и вычисляемых выражений нет. Неизвестная переменная вызывает
ошибку выгрузки, чтобы в итоговом документе не остались незаполненные метки.

## Сопоставление этапов

HR/admin открывает **Настроить этапы**, добавляет/редактирует «Этап с датами» и
выбирает **Соответствует этапу в документе**. Связь хранится по постоянному ключу,
переименование поля её не меняет. Один пункт документа связан максимум с одним
полем компании, включая архивные поля. Для переноса связи сначала очистите её у
прежнего поля. Начальные сопоставления нужно выбрать вручную: имена существующих
полей миграция не интерпретирует.

Список пунктов документа: `backend/app/templates/onboarding/stages.json`.
Чтобы добавить пункт после утверждения шаблона:

1. Добавьте постоянный ключ и название в `stages.json`, например
   `"safety": "Инструктаж по безопасности"`.
2. Добавьте в `variables.json` соответствие
   `"safety_planned_date": "stages.safety.planned_date"`.
3. Вставьте в DOCX `{{ safety_planned_date }}`.
4. HR/admin выбирает новый пункт в настройках нужного этапа.

Изменения этих JSON-файлов не требуют новой миграции или пересборки frontend.
Ключи используйте в формате латинских идентификаторов с подчёркиваниями.

## Утверждённый шаблон

Пока шаблон не утверждён, сервер создаёт простой базовый DOCX автоматически.
После утверждения сохраните файл на сервере и задайте абсолютный путь:

```dotenv
ONBOARDING_DOCX_TEMPLATE=/opt/bookhr/templates/onboarding_plan.docx
```

Перезапустите backend. При использовании контейнера файл необходимо смонтировать
в контейнер, а путь должен существовать внутри контейнера. Форматирование и
картинки шаблона сохраняются. При неверном пути выводится ошибка; незаметного
возврата к базовому документу нет. Новых Python-зависимостей не требуется.

## Ответственный отдел

В настройках этапа укажите ответственный отдел и выберите соответствующий этап
документа. Для сопоставленного этапа DOCX добавит курсивную приписку
`(отв 3 отдел)` в конце абзаца с плановой датой. Отсутствующий отдел не выводится.

## Развёртывание

1. Сделайте резервную копию БД и проверьте миграции на тестовом контуре.
2. Убедитесь, что на сервере доступны **обе** миграции:
   - `0020_onboarding_docx.py` — прежний DOCX-этап, включает `document_stage_key`;
   - `0021_onboarding_department.py` — новый этап, добавляет **только** `responsible_department`.
3. Из каталога `backend` с настроенным Flask-приложением выполните:

   ```bash
   flask db current
   flask db heads
   flask db history
   flask db upgrade
   flask db current
   ```

4. Пересоберите frontend и перезапустите backend.
5. В настройках этапов назначьте ответственных и сопоставьте этапы документа.

Цепочка ревизий: `0019_onboarding_cards` → `0020_onboarding_docx` → `0021_onboarding_department`.

При текущей версии БД `0020_onboarding_docx` применяется только `0021`.
При `0019_onboarding_cards` применяются последовательно `0020` и `0021`.

**Важно:** если в таблице `alembic_version` находится ошибочная промежуточная
ревизия `0020_onboarding_department`, не выполняйте автоматический upgrade
и не применяйте `stamp` без проверки фактических столбцов и истории БД.
Такая БД требует отдельного согласования ревизии с уже выполненным DDL.
