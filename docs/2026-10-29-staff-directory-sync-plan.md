# План интеграции BookHR с внешним кадровым сервисом

Дата: 29.10.2026.
Репозиторий: IvLix13/bookhr.
Статус: реализовано в отдельной ветке; включение на рабочем сервере выполняется после настройки URL и API-ключа.
Основание: требования пользователя и проверенный код main на коммите `e2161b224238994ca92c40f7eb72bb8fc2c39d5c`.

## 1. Цель и принятые решения

Обогащать существующие карточки сотрудников данными внешнего сервиса через фоновый воркер. Внешний сервис — источник истины для сокращённого ФИО, номера карточки, должности и формального отдела. При однозначном сопоставлении изменения применяются автоматически, без подтверждения каждого расхождения.

Используем ровно шесть полей ответа:

- `cardnumber` — единый идентификатор человека между компаниями;
- `fio_short` — сокращённое ФИО;
- `position_name` — полная должность;
- `position_short_name` — сокращённая должность;
- `formal_department_short_name` — сокращённое название формального отдела;
- `formal_department_name` — полное название формального отдела.

`staff_id`, `rank`, `rank_short`, `factual_department_short_name` и `factual_department_name` не сохранять и не использовать в бизнес-логике.

Под «отделом» в интерфейсе понимается формальный отдел. Отдельное дублирующее поле `department` не нужно: использовать два названия формального отдела.

Полное ФИО, даты приёма и увольнения, компании, договоры, паспорта, образование, награды и планы ввода в должность остаются в управлении BookHR. Внешний ответ не содержит данных для их изменения.

## 3. Модель данных и совместимость

### 3.1. Человек: Person

Добавить nullable-поля:

| Поле | Предлагаемый тип | Правила |
| --- | --- | --- |
| `cardnumber` | `String(128)` | Уникальное ограничение на всю таблицу `persons`, а не на компанию. Сохранять как строку с ведущими нулями; пустую строку нормализовать в NULL. |
| `fio_short` | `String(256)` | Сокращённое имя из сервиса; не заменяет `PersonNameHistory.full_name`. |

Размеры строк — проектное решение, поскольку ограничения длины в контракте сервиса не предоставлены. При превышении выдавать понятную ошибку записи, без молчаливого усечения.

Один человек в разных компаниях имеет один `cardnumber`. Не создавать новые `Person`, не менять `uuid` и не объединять существующих людей автоматически. Если разные локальные `Person` претендуют на один номер, фиксировать конфликт сопоставления.

### 3.2. Трудоустройство: Employment

Добавить nullable-поля:

- `formal_department_short_name: String(256)`;
- `formal_department_name: Text`.

Отдел относится к работе в компании. Не хранить его в `Person` и не подменять им `OnboardingColumn.responsible_department`: ответственный за этап онбординга — другая сущность.

Первую версию делать без отдельного справочника отделов и без отдельной таблицы истории отделов. Изменения фиксировать в существующем аудите.

### 3.3. История должностей: PositionHistory

Добавить `short_title: String(256), nullable=True`.

Не создавать второе независимое хранилище полного названия должности. Сопоставление:

| Поле сервиса/API BookHR | Хранилище |
| --- | --- |
| `position_name` | Текущая `PositionHistory.title` |
| `position_short_name` | Текущая `PositionHistory.short_title` |

Сохранить существующее поле API `title` для совместимости; `position_name` возвращать как его согласованный псевдоним. Все текущие экраны и выгрузки, читающие должность из истории, должны получать обновлённое название.

Расширить `update_position` необязательным именованным аргументом сокращённой должности. Отсутствие аргумента в старых вызовах означает «сохранить текущее значение», а явный NULL — «очистить». Проверить создание, редактирование, повторный приём и Excel-импорт, чтобы они случайно не сбрасывали сокращённое название.

При изменении полного или сокращённого названия создавать одну новую актуальную запись истории. При одинаковых значениях ничего не создавать. Дата изменения — дата наблюдения в Москве; внешний сервис не передаёт дату фактического перевода.

### 3.4. Грейды полностью исключены из синхронизации

При обновлении должности передавать в новую историческую запись прежний `position_grade_id`. Если текущей должности нет, не определять грейд из названия или ответа сервиса.

Воркер не вызывает `sync_actual_grade`, не меняет `EmployeeGradeHistory`, каталог грейдов, дату назначения, сроки доступности и грейдовые события. Даже значения `rank`/`rank_short`, совпадающие с локальными, игнорируются.

## 4. Контракт внешнего запроса

Создать отдельный клиент `backend/app/services/staff_directory_client.py`.

Запрос:

```http
GET {STAFF_DIRECTORY_BASE_URL}/staff/placement/public/?last_name=Иванов&first_name=Иван&patronymic=Иванович
X-Api-Key: <STAFF_DIRECTORY_API_KEY>
```

- Использовать `requests.Session`, `params`, таймаут 30 секунд и `raise_for_status()`.
- Не передавать `patronymic`, если отчества нет.
- Сохранять проверку TLS по умолчанию; адрес и ключ получать только из конфигурации окружения.
- Обрабатывать только разрешённые шесть полей; остальные ключи ответа игнорировать.
- Проверять техническую форму ответа: JSON-объект, обязательный список `people`, объекты внутри списка, допустимые типы выбранных полей. Отсутствие `people` считать ошибкой контракта, а не результатом «не найден».
- Доверие данным не отменяет необходимость выбрать правильного человека из нескольких результатов.
- Не сохранять полный внешний ответ в БД или логах.

## 5. Сопоставление сотрудников

### 5.1. Подготовка локального ФИО

В BookHR сейчас хранится одна строка полного ФИО, а запрос требует фамилию, имя и отчество отдельно.

Для первой версии принять поддерживаемый формат «Фамилия Имя [Отчество]»: убрать лишние пробелы, сохранить дефисы и реальные буквы имени. Два компонента — запрос без отчества, три — с отчеством.

Одно слово, инициалы и неоднозначное составное имя не разбирать догадками: пропуск с причиной `invalid_local_name`. Не восстанавливать имя или отчество из `fio_short`. Ограничение указать в эксплуатационной инструкции.

### 5.2. Первичная привязка

1. Получить актуальное полное ФИО через `get_current_name`.
2. Выполнить поиск во внешнем сервисе.
3. Если `people=[]`, отметить `not_found`; локальные данные не менять.
4. Для ещё не связанного человека автоматически принимать только единственный результат с непустым `cardnumber`.
5. Если результатов несколько, не выбирать первый и не считать сокращённое ФИО достаточным идентификатором: отметить `ambiguous`.
6. Проверить, что номер не принадлежит другому локальному `Person`; при конфликте ничего не перепривязывать.
7. Сохранить номер, сокращённое ФИО, должность и формальный отдел в одной транзакции после проверки применимости к трудоустройству.

Если одинаковое полное ФИО есть у нескольких разных локальных `Person`, не назначать единственный внешний номер первому попавшемуся человеку. До автоматической привязки выявлять такой конфликт для всей группы.

### 5.3. Повторные обновления

Если `Person.cardnumber` уже заполнен, в выдаче поиска выбирать запись строго с этим номером. Это позволяет отсеять однофамильцев, даже если `people` содержит несколько человек.

Если совпадений номера нет или одному номеру соответствуют несколько записей ответа, пропустить обновление и зафиксировать причину. Не заменять сохранённый номер другим результатом поиска по ФИО.

Предоставленный endpoint поддерживает только поиск по ФИО. Наличие поиска непосредственно по `cardnumber` не подтверждено: не придумывать такой параметр. Если локальное ФИО устарело и поиск не вернул нужный номер, автоматическое обновление пока невозможно.

### 5.4. Человек и несколько компаний

В ответе нет идентификатора компании или трудоустройства. Поэтому один глобальный `cardnumber` сам по себе не позволяет распределить разные должности и отделы по нескольким одновременно действующим работам человека.

Безопасное правило первой версии:

- при единственном активном трудоустройстве человека применять должность и отдел к нему;
- при нескольких активных трудоустройствах не размножать один внешний набор по всем компаниям, а выдавать `ambiguous_employment`;
- проверять все активные трудоустройства человека, даже при запуске с фильтром `--company-id`;
- общие реквизиты `Person` можно синхронизировать после однозначной идентификации, отдельно от пропущенных реквизитов трудоустройства; отражать частичный результат в отчёте;
- уволенные и исторические трудоустройства по умолчанию не обновлять.

Если понадобится синхронизация разных размещений одного человека, потребуется дополнение контракта внешнего сервиса. Это известное ограничение, не препятствующее планированию первой версии.

## 6. Применение данных и обработка ошибок

Создать сервис `backend/app/services/staff_directory_sync.py`.

- Обрабатывать существующих активных сотрудников небольшими порциями, один внешний запрос на человека за проход.
- Внешний HTTP-запрос выполнять вне длительной транзакции с блокировками.
- Перед записью повторно проверить актуальное ФИО, привязку номера и активные трудоустройства; при изменениях во время запроса пропустить устаревший результат.
- Атомарно применять разрешённые изменения человека и допустимого трудоустройства, сохранять аудит только реально изменённых полей.
- Проверять уникальность номера в приложении и в БД; конкурентный конфликт откатывает изменения этого человека.
- Сравнивать старые и новые значения: повторный проход без изменений не создаёт историю должностей и аудит обновлений.
- Отсутствующий ключ ответа не меняет старое значение; переданный NULL или пустая строка очищает соответствующий описательный реквизит.
- Исключение: пустой `cardnumber` не удаляет связь и не допускает первичную привязку; запись пропускается как `missing_cardnumber`.
- Для пустой полной должности использовать существующее представление «Не указана», так как `PositionHistory.title` обязателен. Сокращённое название и отдел допускают NULL.
- Не менять ничего при ошибке JSON/контракта, таймауте или HTTP-ошибке; `people=[]` не означает увольнение или удаление.
- 400: записать ошибку конкретного запроса без повторов; 401/403: завершить проход с ошибкой конфигурации; 429: учитывать `Retry-After`, не устраивать плотный цикл; таймауты/5xx: ограниченные повторы с нарастающей задержкой.
- Все повторы ограничить количеством и общим временем; при слишком большом `Retry-After` завершить проход и оставить работу следующему запуску.
- Изолировать ошибки отдельных сотрудников: откатить их транзакцию и продолжить, кроме ошибок авторизации/конфигурации и системной недоступности.
- Не создавать отсутствующих сотрудников, компании, договоры и увольнения по внешнему ответу.

Не вводить очередь, Redis или Celery для первой версии: текущий способ фонового запуска позволяет обойтись существующими зависимостями.

## 7. Запуск воркера

Добавить в `backend/app/cli.py` команду:

```bash
flask sync-staff-directory --dry-run
flask sync-staff-directory --company-id 1
flask sync-staff-directory --person-id 123
flask sync-staff-directory
```

`--person-id` — локальный `Person.id`, не внешний `staff_id`. При сочетании фильтров человек должен принадлежать выбранной компании.

`--dry-run` делает реальные запросы и показывает предполагаемые изменения, но не меняет поля, timestamps, историю и аудит. В итоговом отчёте показывать: просмотрено, обновлено, без изменений, частично обновлено, не найдено, неоднозначное ФИО, конфликт номера, неоднозначное трудоустройство, ошибки запроса.

Добавить настройки в `backend/app/config.py` и `.env.example`:

- `STAFF_DIRECTORY_ENABLED=false`;
- `STAFF_DIRECTORY_BASE_URL=`;
- `STAFF_DIRECTORY_API_KEY=`;
- `STAFF_DIRECTORY_TIMEOUT=30`;
- `STAFF_DIRECTORY_BATCH_SIZE=100`;
- `STAFF_DIRECTORY_MAX_RETRIES=2`.

Значения интервала и размера пачки — предлагаемые настройки первой версии, а не требования внешнего сервиса.

Создать `deploy/bookuchet-staff-sync.service` и `deploy/bookuchet-staff-sync.timer` по существующему образцу. Предложение по расписанию — раз в час; не включать timer до заполнения настроек и проверки ручного `--dry-run`. Часовой пояс расписания описать явно.

Для одновременного ручного и системного запуска предусмотреть общую блокировку на время прохода, например PostgreSQL advisory lock в производственном контуре. Повторный процесс должен завершаться с понятным результатом «синхронизация уже запущена». Уникальное ограничение `cardnumber` оставить независимо от блокировки.

Коды завершения: 0 — проход без технических ошибок, в том числе «без изменений»/«не найдено»; ненулевой — ошибки конфигурации, HTTP или записи. Неоднозначные соответствия перечислять отдельно, не скрывать за числом успешных обновлений.

## 8. API и интерфейс «Все сотрудники»

### API

В `employment_to_dict` добавить шесть согласованных реквизитов, сохранив `title`, полное ФИО и локальные грейды.

Для старых записей возвращать NULL у новых необязательных реквизитов; `position_name` получать из существующей актуальной должности. В сериализаторе не делать сетевых запросов.

Если поддержать запись `position_name` через существующий CRUD, нормализовать его в `title` в одном месте. При одновременных разных `title` и `position_name` возвращать ошибку, а не выбирать значение неявно.

Сохранить текущие права admin/hr/viewer и изоляцию компаний. Внешний API-ключ и технический endpoint не отдавать браузеру. Для фонового CLI не отключать защиту пользовательских API.

### Таблица

В `frontend/src/views/EmployeesView.vue` добавить колонку «Отдел» рядом с должностью:

- основное значение — `formal_department_short_name`;
- если сокращённого нет — `formal_department_name`;
- полное название показывать в подсказке;
- если нет обоих — «—».

Полное ФИО оставить основным идентификатором строки. Не перегружать общую таблицу всеми внешними реквизитами.

Серверную сортировку отдела добавить в `backend/app/api/employees.py`; она должна работать по всему набору, до пагинации. Сортировать по отображаемому значению с тем же правилом сокращённое → полное → NULL, включая пустые строки.

### Карточка сотрудника

Обновить `EmployeeForm.vue` и тип `Employee` в `frontend/src/types/index.ts`:

- показать `cardnumber`, `fio_short`, оба названия должности и оба названия отдела;
- оставить грейды отдельными локальными полями;
- сохранить существующие права просмотра и редактирования;
- для новых реквизитов в старых карточках корректно отображать отсутствие значения.

Сохранить действующий ручной CRUD для admin/hr; пояснить в карточке, что при включённой синхронизации сервис автоматически обновляет внешние реквизиты. Изменение `cardnumber` проверять на глобальную уникальность и фиксировать в аудите; не делать перепривязку молча.

Текущий Excel-импорт не расширять внешними полями в первой версии, но проверить, что отсутствие новых колонок не затирает сохранённые реквизиты. Внешняя синхронизация при следующем проходе остаётся источником актуальной должности и отдела.

Поиск по новым реквизитам и отдельный экран управления конфликтами не обязательны для первой версии. Не менять общий поиск во всех модулях без отдельной необходимости.

## 9. Миграция и порядок реализации

1. Обновить рабочую ветку от актуальной main; проверить действующие инструкции репозитория и вершину Alembic.
2. Создать следующую миграцию (ожидаемое имя `0025_staff_directory_fields.py`, если номер остаётся свободным).

8. Пройти проверки ниже с подменённым внешним HTTP-клиентом.
9. На тестовой базе применить миграцию и ручной dry-run; проверить несколько реальных сопоставлений.
10. Выполнить первый контролируемый проход, сверить локальные грейды до/после; затем включить периодический запуск.

При откате сначала остановить timer. Откат миграции удалит новые реквизиты, но сам по себе не восстановит прежние должности: для этого нужны аудит или резервная копия. Указать это в инструкции.

## 11. Проверки и критерии приёмки

- Единственный внешний результат обновляет только выбранные шесть реквизитов существующего сотрудника.
- Полная должность становится видна через старое поле `title` и новое `position_name`; сокращённая хранится отдельно.
- В «Все сотрудники» виден формальный отдел; полное название доступно в карточке/подсказке; серверная сортировка работает между страницами.
- Произвольные `rank`/`rank_short` не меняют фактический грейд, грейд по должности, даты и грейдовые события. Отдельно проверить смену должности при заполненном `position_grade_id`.
- Повтор того же ответа не создаёт лишних записей истории и аудита.
- Номер с ведущими нулями сохраняется без преобразования в число.
- Одинаковый номер у двух локальных людей вызывает конфликт, а не объединение.
- Пустой номер, несколько внешних кандидатов, одинаковое локальное ФИО и несколько активных трудоустройств обрабатываются по правилам раздела 5.
- При известном номере выбирается именно он; другой номер не подменяет связь.
- ФИО без отчества отправляется без параметра `patronymic`; инициалы и неоднозначные составные имена не разбираются автоматически.
- Явно пустые описательные значения, отсутствующие ключи и пустой номер имеют различное, описанное выше поведение.
- 400/401/403/429/5xx, таймаут, невалидный JSON и отсутствие `people` не стирают прежние данные; число повторов ограничено.
- Dry-run не меняет БД и аудит; ошибка одного сотрудника не откатывает уже успешно обработанных.
- Два запуска не проходят одновременно; гонка за номер обрабатывается уникальным ограничением.
- Запрос, начатый до ручной смены ФИО/номера или увольнения, не применяет устаревший результат.
- Уволенные периоды не получают новую текущую должность; отбор компании не обходит проверку нескольких активных работ.
- Старые карточки, ручное сохранение, повторный приём и Excel-импорт работают без новых обязательных полей и потери сокращённой должности.
- Экспорт DOCX продолжает использовать актуальную должность; отдел сотрудника не заменяет ответственные отделы этапов.
- Viewer сохраняет просмотр без права записи; изоляция компаний не нарушена.
- Миграция проверена на тестовой SQLite и копии PostgreSQL; сохранены существующие записи.
- API-ключ отсутствует в git, браузерных ответах и журналах.

Реализация выполнена по отдельному запросу пользователя. Миграцию рабочей базы и включение timer выполнить при развёртывании по инструкции.

## Дополнение при реализации: более 150 сотрудников

По уточнению пользователя введены последовательные запросы с паузой минимум 2 секунды, случайная добавка 0–0,5 секунды, сохранение времени последней проверки человека (по умолчанию 6 часов), лимиты 500 HTTP-попыток и 30 минут за проход. Все повторы учитываются в лимитах. При 429 проход останавливается, общий Retry-After сохраняется для следующих запусков; после трёх подряд технических ошибок включается пауза. Общая блокировка предотвращает параллельные проходы разных компаний. Добавлены только технические отметки, помимо шести согласованных бизнес-полей. Подробности эксплуатации — в [staff-directory.md](staff-directory.md).
