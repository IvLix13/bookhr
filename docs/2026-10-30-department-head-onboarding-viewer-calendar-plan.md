## 1. Результат

1. При открытии плана ввода в должность показывать полную должность сотрудника и ФИО в формате «Фамилия И.О.». Внизу плана разместить сведения о его начальнике: полная должность, ФИО в том же формате и фактический локальный грейд.
2. В DOCX использовать те же реквизиты: сотрудник в начале документа, начальник отдела после этапов. Для пользовательского шаблона предоставить плейсхолдеры.
3. Начальник определяется автоматически: активный сотрудник той же компании с тем же номером отдела, текущая полная должность которого начинается со слов «начальник отдела».
4. Все учётные записи с ролью viewer получают календарь только с событиями сотрудников своего отдела. Права на изменение событий не предоставляются.

Начальник отдела и наставник/куратор — разные сущности. Наставник остаётся независимо заданным в плане.

## 3. Единый идентификатор отдела

### 3.1. Проверить источник номера перед реализацией

Требование пользователя — сравнивать номер отдела. Код подтверждает наличие двух названий отдела, но не доказывает, что какое-либо поле содержит именно номер.

Первый шаг реализации: проверить реальный обезличенный пример сохранённых значений и контракт внешнего сервиса.

- Если `formal_department_short_name` уже содержит стабильное обозначение/номер отдела, использовать его как единый ключ для обеих функций.
- Если это только название без однозначного номера, определить настоящее поле номера во внешнем контракте и добавить `Employment.department_number` вместе с синхронизацией, сериализацией и миграцией. Не придумывать имя внешнего поля.
- Не извлекать произвольную последовательность цифр из полного названия или должности. Не считать `cardnumber` номером отдела: это идентификатор человека.
- Источник ключа должен быть единым для всех сотрудников. Не смешивать полное и сокращённое название через индивидуальные fallback-правила.

Выделить общий сервис `backend/app/services/departments.py`: получение и нормализация ключа отдела, запрос сотрудников отдела. Остальной код обращается к нему, а не дублирует сравнения.

### 3.2. Правила сравнения

- Сравнение только внутри одной компании.
- Ключ хранить/обрабатывать как строку: не терять ведущие нули и составные обозначения.
- Допустима нормализация крайних/повторяющихся пробелов и регистра букв. Не менять смысл номера и не объединять «01» и «1» без подтверждённого правила источника.
- Только точное равенство нормализованных ключей. Отделы «1» и «10» различны.
- NULL, пустая строка и пробелы означают «отдел не определён». Два отсутствующих отдела не образуют общий отдел.
- Ответственный отдел этапа `OnboardingColumn.responsible_department` в этом сравнении не участвует.
- Поиск начальника и чтение календаря используют сохранённые данные BookHR без запросов во внешний сервис.

Если понадобится отдельный номер, включить его в snapshot-проверку синхронизации, аудит, обработку отсутствующего ключа/явного NULL и существующие тесты синхронизации. Сохранить действующие ограничения нагрузки.

## 4. Автоматическое определение начальника

Добавить `backend/app/services/department_heads.py` с общей функцией определения начальника для конкретного трудоустройства.

Алгоритм:

1. Получить компанию и непустой ключ отдела выбранного сотрудника.
2. Выбрать активные трудоустройства той же компании с точно тем же ключом отдела.
3. Исключить самого сотрудника: сотрудник не назначается собственным начальником.
4. Проверить актуальную полную должность из истории; использовать существующий способ получения текущей должности.
5. Нормализовать пробелы и регистр. Принимать должность, начинающуюся с «начальник отдела» с границей слова после «отдела». Например, «Начальник отдела информационных технологий».
6. Не принимать «заместитель начальника отдела», «помощник начальника отдела», «главный специалист отдела». В первой версии «и. о. начальника отдела» не считать начальником автоматически.
7. Один кандидат — найденный начальник; ноль — не найден; несколько — неоднозначность. Не выбирать первого по ID, алфавиту или максимальному грейду.
8. Полную должность взять из текущей истории должностей; фактический грейд — из локальной `EmployeeGradeHistory`, через существующий `get_current_grade`. Внешние `rank/rank_short` и грейд должности не подменяют фактический грейд.

Результат: статус `found | department_missing | not_found | ambiguous` и объект начальника либо NULL. При отсутствии должности/грейда отображать «—», не завершать запрос ошибкой.

Если план составляется для самого начальника отдела, поиск вышестоящего руководителя не выполнять: это выходит за пределы правила «тот же отдел + начальник отдела».

Связь вычисляется при чтении по текущим данным, а не фиксируется в плане. Смена отдела или начальника отражается после обновления данных. Начальник, отсутствующий в локальной базе, не будет найден: существующая синхронизация не импортирует новых людей. Это ограничение описать в документации.

Для списков планов предусмотреть групповую загрузку должностей, грейдов и кандидатов по отделам; избежать отдельного запроса на каждый план. Не создавать новую миграцию для хранения вычисляемого начальника.

## 5. План ввода в должность: API, интерфейс и DOCX

### 5.1. Данные API

Расширить сериализацию плана совместимыми полями:

- `employee_short_name` — «Фамилия И.О.»;
- `employee_position` — полная текущая должность;
- `department_key` и отображаемое название отдела;
- `department_head_status`;
- `department_head`: `employment_id`, `short_name`, `position`, `grade` либо NULL.

Существующее `full_name` сохранить: оно используется поиском, заголовками и текущей проверкой права viewer редактировать собственный план. Изменение визуального ФИО не должно менять эту проверку. Права онбординга этим заданием не расширять и не ограничивать.

Общее форматирование ФИО использовать и в API, и в DOCX. При корректном `Person.fio_short` привести его к «Фамилия И.О.»; при отсутствии/неподходящем формате сформировать инициалы из актуального полного ФИО существующим способом. Не сокращать уже сокращённое имя повторно. Проверить два/три компонента и фамилии с дефисом.

### 5.2. Интерфейс

В `OnboardingPlanModal.vue`:

- сверху показать «Полная должность · Фамилия И.О.» либо две строки для длинной должности;
- сохранить грейд сотрудника, наставника и прогресс;
- под таблицей этапов разместить компактный блок «Начальник отдела»: полная должность, ФИО, фактический грейд;
- при отсутствии данных показать понятное состояние: «Отдел не указан», «Начальник отдела не найден» или «Найдено несколько начальников отдела»;
- сохранить стиль приложения, ширину до 1500 px, прокрутку этапов и sticky-шапку; новый нижний блок не должен вытеснять таблицу за границы окна.

ФИО начальника добавляется как пояснение к его должности и грейду. Ручной выбор начальника и редактирование его реквизитов в плане в первую версию не входят.

### 5.3. DOCX

Сохранить имена существующих переменных сотрудника:

| Плейсхолдер Word | Значение |
| --- | --- |
| `{{ employee_position }}` | Полная должность сотрудника |
| `{{ employee_name }}` | Фамилия И.О. сотрудника |
| `{{ employee_grade }}` | Фактический грейд сотрудника |
| `{{ department_head_position }}` | Полная должность начальника |
| `{{ department_head_name }}` | Фамилия И.О. начальника |
| `{{ department_head_grade }}` | Фактический локальный грейд начальника |

В `variables.json` добавить источники `department_head.position`, `department_head.short_name`, `department_head.grade`; расширить `document_context` тем же сервисом определения начальника.

В автоматически создаваемом шаблоне сотрудник располагается перед этапами, начальник — после всех этапов. В пользовательском DOCX положение определяется местом вставки плейсхолдеров; автоматически дописывать строки в загруженный шаблон не нужно. Старые шаблоны без новых переменных продолжают работать.

При отсутствии/неоднозначности начальника экспорт не блокировать: значения новых переменных «—», причину показать в интерфейсе. Обновить `docs/onboarding-docx.md` примером размещения блока внизу документа. Сохранить существующие подстановки дат и ответственных отделов, обработку разбиения плейсхолдеров Word на runs и форматирование.

## 6. Связь viewer с сотрудником

По одному отображаемому ФИО нельзя надёжно определить отдел учётной записи. Добавить явную административную привязку:

1. Nullable FK `User.employment_id -> employments.id` с индексом, relationship и `ON DELETE SET NULL`.
2. Новую Alembic-миграцию после актуального head. При текущей базе следующая после `0025_staff_directory_fields`; номер и down_revision перепроверить непосредственно перед реализацией.
3. В настройках пользователей добавить поле «Сотрудник» с серверным поиском и пагинацией: сотрудников более 150, одной первой страницы недостаточно. Показывать ФИО, должность и отдел для различения однофамильцев.
4. Разрешить привязку/смену/снятие только администратору; проверять принадлежность трудоустройства компании пользователя. Не принимать отдел или чужой employment_id от viewer.
5. Поддержать локальные и LDAP-учётные записи через существующий административный CRUD. Повторный LDAP-вход не должен сбрасывать привязку.
6. В `/me` возвращать текущий статус доступности календаря, отдел и причину отсутствия области доступа. Сведения читать из актуального трудоустройства.
7. Существующие пользователи получают NULL. Автоматически привязывать по совпадению ФИО не нужно. Дать админу возможность быстро найти непривязанных viewer.
8. После увольнения, удаления или отсутствия отдела у привязанного сотрудника область доступа viewer считается неопределённой. При повторном приёме администратор явно выбирает новое трудоустройство.

Не копировать номер отдела в User: иначе перевод сотрудника создаст рассогласование. Область доступа вычислять на сервере при каждом запросе; не доверять старому отделу из браузера или сессии.

Проверить существующее удаление сотрудников: оно должно обнулять привязку и не падать из-за нового FK. Несколько учётных записей могут ссылаться на одного сотрудника; уникальность employment_id не требуется.

## 7. Серверная область видимости событий

Добавить единый сервис `backend/app/services/event_visibility.py`, применяемый ко всем разрешённым viewer путям чтения событий.

### 7.1. Правило

- admin/hr: существующий доступ внутри своей компании.
- viewer: событие принадлежит компании пользователя, связано через `Event.employment_id` с сотрудником этой компании, ключ его отдела совпадает с ключом отдела привязанного viewer.
- События без сотрудника, с неизвестным отделом или из другой компании viewer не получает.
- Статус увольнения целевого сотрудника сам по себе не добавляет нового фильтра: применяются существующие фильтры событий и совпадение сохранённого отдела. Для самого viewer активное трудоустройство обязательно.
- Фильтрация по текущему сохранённому отделу; исторический отдел на дату события отдельно не восстанавливается.
- Если область viewer неопределённа: списки пусты, счётчики нулевые; отдельное событие недоступно с 404. В интерфейсе причина берётся из статуса доступа `/me`.
- Изменение отдела в БД должно отражаться со следующего запроса без повторного входа.
- Параметры `company_id`, `department`, `employment_id`, `categories` от клиента могут только дополнительно сузить разрешённую выборку, но не расширить её.

Применять SQL-ограничение до сортировки, limit, пагинации и расчёта total/pages. Для единичного события искать сразу в разрешённой выборке. Ограничение не должно зависеть от того, открыт запрос из календаря или отправлен вручную.

### 7.2. API

| Маршрут | Изменение для viewer |
| --- | --- |
| `GET /api/events` | Разрешить чтение с общей областью отдела; месяц и выбранный день используют её. |
| `GET /api/events/upcoming` | Та же область до limit. |
| `GET /api/events/<id>` | Разрешить только видимое событие; чужое/отсутствующее — одинаковый 404. |
| `GET /api/attention` | Только категория событий своего отдела, включая связанные счётчики. Другие кадровые категории для viewer не собирать и не возвращать даже при явном categories. |
| Создание/изменение/удаление/complete/cancel/reopen | Сохранить запрет viewer на сервере. |

Не расширять доступ viewer к закрытым разделам «События», «Грейды», «Поощрения», «Статистика», «Награды за стаж», «Импорт» и административным настройкам. Доступ к чтению event API нужен календарю, самостоятельный маршрут списка «События» остаётся закрытым.

Проверить сериализацию видимого события: контекст завершения и связи не должны раскрывать записи других отделов/компаний. Viewer не нужен список кандидатов для изменения грейда или другие данные форм действий. Проверить фактический граф связанных данных и исключить из viewer-ответа лишние данные для операций.

Существующие права других модулей не заменять глобальной фильтрацией всех сотрудников по отделу: задача ограничивает календарные события.

## 10. Проверки и критерии приёмки

### Начальник и план

- Один активный начальник того же отдела/компании определяется; другие отделы, компании и уволенные кандидаты не участвуют.
- Регистр/лишние пробелы не мешают; «заместитель начальника отдела» не подходит.
- Отсутствующий отдел, отсутствие начальника и несколько кандидатов обрабатываются явно.
- План самого начальника не назначает его самому себе.
- Выводится полная должность; ФИО строго «Фамилия И.О.» без повторного сокращения.
- Фактический грейд берётся из локальной истории, включая отсутствие грейда.
- Данные UI и DOCX согласованы; старый DOCX работает; новые плейсхолдеры заполняются, включая таблицы и разорванные Word runs.
- Наставник, даты этапов, общий прогресс и действующие права онбординга сохраняются.

### Viewer и календарь

- Два viewer одного отдела видят одинаковый набор событий этого отдела.
- Viewer другого отдела не видит чужие события в месяце, дне, ближайших, attention, счётчиках и по ID.
- Проверены «1»/«10», «01»/«1», пустые отделы и одинаковый номер в разных компаниях.
- Подмена query-параметров не расширяет доступ.
- Ограничение применяется до пагинации/limit; total/pages не включают чужие события.
- События без сотрудника viewer не получает.
- Непривязанный/уволенный viewer получает пустой календарь с объяснением.
- Перевод сотрудника/viewer в другой отдел учитывается со следующего запроса.
- Viewer не может менять привязку, отдел и события; admin/hr сохраняют прежние возможности.
- Закрытые ранее кадровые разделы остаются закрытыми; календарные GET исключены из тестов полного запрета и заменены проверками области доступа.
- Неавторизованные запросы по-прежнему требуют входа.

### Миграция и эксплуатация

- Upgrade на существующей БД и чистой БД; существующие пользователи сохраняются с NULL-привязкой.
- Удаление сотрудника обнуляет FK, повторный LDAP-вход сохраняет привязку.
- Проверка на PostgreSQL обязательна для запросов с историей/пагинацией; SQLite — по действующему тестовому окружению.
- Открытие плана/календаря не создаёт внешних HTTP-запросов. Набор 150+ сотрудников не ограничивается первой страницей.
- Запустить профильные backend/frontend-тесты и штатную проверку типов/сборку frontend из scripts проекта.

## 11. Порядок реализации и включения

1. Проверить источник номера отдела и актуальный migration head; зафиксировать ключ в документации.
2. Реализовать общий ключ отдела и определение начальника с тестами.
3. Добавить привязку User → Employment, миграцию и административный UI.
4. Добавить реквизиты сотрудника/начальника в план и DOCX.
5. Реализовать серверную область доступа event API и event-only attention для viewer.
6. Открыть viewer маршрут/пункт календаря, проверить состояния и прямые ссылки.
7. Обновить регрессионные тесты и документацию; выполнить проверки.
8. Перед установкой сделать резервную копию БД, применить миграцию и обновить backend/frontend согласованно.
9. Администратор привязывает существующие viewer к сотрудникам и проверяет отделы. До привязки у viewer пустой календарь.
10. Проверить на двух отделах и учётных записях admin/hr/viewer. Зафиксировать, что данные актуальны на момент последней синхронизации; отдельной мгновенной загрузки внешнего сервиса эта функция не требует.
