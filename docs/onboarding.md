# План обучения: использование и развёртывание

## Возможности

Раздел «План обучения» расположен после «Сотрудники». HR/admin вручную добавляет существующего сотрудника. На каждый период трудоустройства разрешён один план; повторный приём позволяет создать другой план.

Каждый сотрудник отображается отдельной карточкой: ФИО, актуальный грейд, отдел, дата прибытия, куратор, процент выполнения, счётчики и ближайший незавершённый этап. Фото и телефон не используются, место под них не резервируется. «Открыть план» раскрывает этапы и ручные поля с плановыми и фактическими датами; несколько карточек могут быть открыты одновременно. После сохранения или обновления открытые карточки остаются раскрытыми. Поиск и пагинация работают по сотрудникам (25 на страницу).

Отдел берётся из активного текстового поля с названием «Отдел», дата прибытия — из активного поля типа «Дата» с названием «Дата начала». Регистр и крайние пробелы названия не важны. Если дата начала не заполнена, используется дата приёма сотрудника. При переименовании этих полей они остаются в деталях; сводка показывает «Отдел не указан» и дату приёма. Куратор хранится отдельно в плане как ФИО; HR/admin меняет его через «Изменить куратора» в раскрытом плане. Пустое значение снимает назначение. Viewer не может менять куратора, включая собственный план. Конфликт версий не позволяет перезаписать чужое изменение.

Процент = округлённое до целого количество выполненных этапов / количество требуемых этапов × 100. Учитываются только активные этапы с датами и без дат; текст, обычные даты, архивные поля и «Не нужно» исключаются. Если требуемых этапов нет, показывается 0% и пояснение «Нет обязательных этапов». Полоса показывает выполненные этапы зелёным, работу жёлтым, просрочку красным, ещё не начатые серым. Число процентов соответствует только выполненной части. Просрочка определяется по московской дате (срок сегодня не просрочен) и имеет приоритет над «В работе»; один этап попадает в один счётчик. Дата пересчитывается каждую минуту, без перезагрузки страницы.

Ближайший этап выбирается из незавершённых требуемых этапов по самому раннему плановому сроку, включая просроченные. Этапы без срока идут после этапов со сроком, в порядке настройки. Когда все требуемые этапы завершены, показывается «Все этапы выполнены».

Кнопка «Скачать Excel» доступна всем авторизованным ролям и выгружает всю таблицу текущей компании независимо от открытой страницы и поисковой строки. В файл входят ФИО, номер, грейд и все неархивные этапы в порядке интерфейса. Выполненные ячейки выделяются лёгким зелёным фоном и в интерфейсе, и в Excel.

Кнопка «Настроить этапы» открывает модальное окно. HR/admin может добавить поле, переименовать, переместить вверх/вниз, архивировать и восстановить. Структура общая для текущей компании. Архивирование скрывает строку у всех сотрудников, не удаляя значения. Смена типа разрешена только для пустого поля, включая отсутствие отметок «Не нужно». При закрытии окна с изменённой формой требуется подтверждение сброса; во время сохранения окно не закрывается. В API сущности по-прежнему называются columns: транспонирование не меняет идентификаторы и данные.

Поддерживаются текст, обычная дата, этап с датами и этап без даты. Нажатие ячейки открывает редактор. Для обоих типов этапов доступен явный статус «В работе», выбираемый вручную в редакторе. Он не означает выполнение и не увеличивает процент. Состояния «Выполнено», «В работе», «Не начато» и «Не нужно» взаимоисключающие. У этапа с датами есть плановый срок и фактическая дата: выбор «Выполнено» подставляет сегодняшнюю дату по Москве, её можно исправить. Завершение без заранее указанного срока разрешено. Отмена выполнения очищает фактическую дату, но сохраняет срок и аудит. Просроченные этапы выделены цветом; выполненные отмечены статусом «Выполнено» и зелёным фоном. Этап без даты сохраняет только состояние, календарей и скрытой даты выполнения нет.

Для обоих типов этапов есть состояние «Не нужно», индивидуальное для сотрудника. Оно снимает выполнение и фактическую дату, сохраняет плановый срок и не считается просрочкой. При возврате к «Не начато» срок снова виден. Для текста и обычной даты этот маркер недоступен.

«Очистить ячейку» обнуляет значение, все даты и все отметки после нажатия «Сохранить». До сохранения очистку можно отменить. Сотрудник и поле остаются, история сохраняется в аудите. Очистка доступна для всех ручных типов. Версия записи увеличивается, поэтому старый редактор не может затереть результат очистки.

Все изменения выполняются по кнопке «Сохранить». При конфликте версий ввод остаётся в форме, но повторное сохранение устаревшей версии запрещено: нужно открыть обновлённую запись заново. Автоматического слияния чужих изменений нет.

Viewer может изменять ячейки только того сотрудника, чьё текущее ФИО совпадает с ФИО пользователя без учёта регистра и крайних пробелов. Это касается текста, дат, состояния этапа, отметки «Не нужно» и очистки. Остальные сотрудники остаются доступны для просмотра. Добавлять сотрудников и менять структуру этапов viewer не может. HR и admin имеют полный доступ: планы, ячейки и настройка этапов. Сервер проверяет роли, ФИО и компанию при каждой операции; существующая CSRF-защита распространяется на новый API.

Увольнение не удаляет план. Удаление сотрудника, у которого есть план, запрещено. Массовая очистка сотрудников также останавливается до удаления каких-либо записей, если есть хотя бы один план. Отдельный интерфейс просмотра аудита не добавлен; записи сохраняются в существующей таблице AuditLog.

## Первоначальные столбцы

Миграция создаёт для существующих компаний шесть ручных столбцов: Отдел (текст), Дата начала (дата), Пропуск, NDA, Экзамен на компетентность, План обучения (этапы).

Остальные столбцы HR/admin добавляет через интерфейс. Число 25 не является ограничением. Для компаний, созданных после миграции, HR/admin формирует структуру с нуля. Планы сотрудников автоматически не создаются.

Импорт планов из Excel, файловые вложения, напоминания и события календаря в модуль не входят.

## Обновление dev/prod, включая офлайн-контур

1. Сделать резервную копию БД и сохранить предыдущую версию приложения.
2. Перенести согласованную версию исходников и собранный фронтенд обычным способом проекта. Новых Python/npm-зависимостей нет.
3. На тестовом контуре выполнить существующий сценарий: `bash scripts/migrate.sh dev`. Проверить раздел, роли и сохранение ячеек.
4. Для prod остановить приложение штатным способом и выполнить `bash scripts/migrate.sh prod` (он также делает резервную копию через pg_dump). Скрипт использует существующий офлайн-набор зависимостей; менять их не требуется.
5. Развернуть пересобранный фронтенд и запустить приложение по обычной схеме проекта. Не обновлять только frontend: требуется backend и миграция вместе.
6. Проверить создание плана, изменение даты, галочку, архивирование и восстановление столбца. Проверить, что viewer сохраняет ячейку сотрудника с тем же ФИО в другом регистре и получает отказ для другого ФИО, а структуру и планы не меняет. Проверить отсутствие доступа к другой компании.

Миграция `0016_onboarding` добавляет onboarding_columns, onboarding_plans, onboarding_cells. Новая `0017_onboarding_states` добавляет `is_not_required` (false для существующих ячеек), тип checkbox и обновляет ограничения. Существующие значения и даты сохраняются. Применить обе до запуска обновлённого приложения. Транспонирование само по себе миграции не требует.

Downgrade `0017_onboarding_states` заранее останавливается, если есть checkbox-поля, маркеры «Не нужно» или выполнение без даты: автоматической потери новых данных нет.

Внимание: downgrade `0016_onboarding` удаляет таблицы обучения и их данные. После начала эксплуатации для отката использовать согласованное восстановление из резервной копии; не запускать downgrade без сохранения данных.

## Проверки разработчика

- Backend: `cd backend && python -m pytest -q`.
- Frontend: `cd frontend && npm run typecheck && npm test && npm run build`.
- Новые тесты: backend/tests/test_onboarding.py и frontend/src/views/OnboardingView.test.ts.
- Миграционный тест проверяет upgrade/downgrade/upgrade на изолированной SQLite БД с уже существующим сотрудником. Проверки на рабочей PostgreSQL БД и развёртывание в prod выполняются отдельно, не этим документом.


## Обновление карточек (0019)

Обновить backend и пересобранный frontend вместе. До запуска выполнить штатную миграцию `bash scripts/migrate.sh dev` или `bash scripts/migrate.sh prod` для соответствующего контура. Новая миграция `0019_onboarding_cards` идёт после `0018_nextcloud_direct_recipients`: добавляет nullable `curator_name` и версию плана (1 для существующих планов), а также `is_in_progress` (false для существующих ячеек). Существующие сроки, значения, выполнение и отметки «Не нужно» сохраняются. Новых зависимостей нет. Откат 0019 запрещён при заполненных кураторах или этапах в работе, чтобы не терять данные.

Excel сохраняет прежнее расположение сотрудников по столбцам и этапов по строкам. Новый статус выгружается как «В работе», у этапа с датами вместе с плановым сроком. Куратор показан в карточке и хранится в плане; отдельная строка куратора в Excel не добавлена.
