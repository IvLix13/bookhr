# План: ответственный отдел для пунктов onboarding и SVG-действия

Дата: 2026-10-22
Статус: план, без реализации

## Цель
Для каждого настраиваемого этапа/поля плана ввода в должность хранить один ответственный отдел; показывать его рядом с пунктом в плане сотрудника и добавлять к названию пункта в DOCX курсивную приписку в скобках, например: *（отв 3 отдел）* (в итоговом документе использовать обычные круглые скобки: `(отв 3 отдел)`). В окне «Настройка этапов и полей» заменить текстовые названия кнопок действий на SVG-иконки без потери доступности.

## Что обнаружено в main
- `backend/app/models/onboarding.py`: этапы и поля представлены общими для компании `OnboardingColumn`; ячейки конкретного сотрудника — `OnboardingCell`.
- `backend/app/services/onboarding.py`: `ColumnSchema`, `ColumnUpdateSchema`, `column_dict`, `save_column` обслуживают структуру и версионирование полей.
- `backend/app/api/onboarding.py`: GET/POST/PATCH `/onboarding/columns`; текущая выгрузка onboarding здесь — XLSX.
- `frontend/src/components/OnboardingColumns.vue`: редактор структуры с текстовыми кнопками; `OnboardingColumnsModal.vue` — модальное окно.
- `frontend/src/components/OnboardingPlanDetails.vue`: таблица пунктов сотрудника.
- `frontend/src/types/onboarding.ts`: интерфейс `OnboardingColumn`.
- В проверенной версии `main` генератор DOCX для плана onboarding не обнаружен. Перед реализацией найти/объединить актуальную ветку с DOCX-выгрузкой; не подменять её XLSX-экспортом и не создавать параллельный несовместимый генератор.

## 1. Данные и миграция
1. Добавить к `OnboardingColumn` необязательное текстовое поле `responsible_department` (имя уточнить по уже существующей доменной модели отделов, если такая есть). Ответственный отдел один на пункт, общий для всех планов этой компании.
2. Создать Alembic-миграцию для существующих БД. Для ранее созданных пунктов значение `NULL`, без автоматического назначения.
3. Допускать изменение/очистку ответственного отдела при любом типе поля (`stage`, `checkbox`, `text`, `date`). Не затрагивать значения `OnboardingCell` и сроки.
4. Проверить, существует ли в проекте справочник отделов. Если да — использовать его идентификаторы и подписи; если нет — обычное необязательное текстовое поле (без создания отдельного справочника в рамках задачи).

## 2. Backend и API
1. Расширить `ColumnSchema` и `ColumnUpdateSchema` полем ответственного отдела (допускается `null`/пустая строка), задать валидацию длины и нормализацию пробелов.
2. Добавить поле в `column_dict` и ответы GET/POST/PATCH, в аудит изменений, сохранить текущий контроль `version` и разделение по `company_id`.
3. Не менять полномочия: создавать/редактировать структуру могут текущие авторизованные роли ADMIN/HR.
4. Убедиться, что прежние клиенты без нового поля продолжают работать, а старые строки отображаются без приписки.

## 3. Настройка этапов и полей
1. В `OnboardingColumns.vue` добавить подписанное поле «Ответственный отдел» рядом с названием и типом. При редактировании загружать текущий отдел; при создании — пустое значение.
2. При сохранении передавать отдел в POST/PATCH; включить его в dirty-check и сброс формы.
3. В перечне полей выводить назначенный отдел компактно, например `Изучение документов · Этап с датами · 3 отдел`.
4. Заменить **текст на кнопках действий** на SVG-иконки: добавить/сохранить, сбросить, редактировать, удалить, архивировать/восстановить, подтвердить/отменить архивирование, переместить вверх/вниз. Заголовки и подписи полей оставить текстовыми.
5. Для каждой иконки сохранить `aria-label`, `title`/tooltip, `type="button"` где не требуется submit, `disabled`, фокус клавиатуры и подтверждения опасных действий. Использовать существующий подход к SVG-компонентам/иконкам проекта, а не новый пакет.
6. Проверить вёрстку модалки `OnboardingColumnsModal.vue` на узких экранах.

## 4. Отображение пункта в плане
1. В `OnboardingPlanDetails.vue` напротив **каждого** пункта вывести «Ответственный отдел» (отдельным столбцом либо компактным вторичным текстом у названия, если таблица станет слишком широкой; приоритет — чёткое соответствие строки и отдела).
2. Если отдел не задан, показывать `—`. Не менять статусы, сроки, обработчики редактирования ячеек и сортировку.
3. Расширить TypeScript-интерфейс `OnboardingColumn` и места составления моков.

## 5. Выгрузка DOCX
1. Найти и проверить текущий код создания DOCX и словарь соответствий полей шаблона; убедиться, что работаем с актуальной реализацией, а не только с XLSX из `main`.
2. При формировании названия каждого экспортируемого пункта добавлять **после основного текста** пробел и `(отв <название отдела>)` в случае, если отдел назначен.
3. Основной текст пункта оставить с текущим форматированием; **только скобки и текст внутри них** сделать курсивом (отдельный Word run), не окрашивать и не изменять шрифт остальных частей. Пример: `Изучение локальных актов` + *`(отв 3 отдел)`*.
4. Если отдел отсутствует — не добавлять пустые скобки. Сохранить существующие переменные DOCX, порядок пунктов и плановые даты.
5. Проверить работу с заменяемыми placeholder'ами/табличными ячейками: `docxtpl` и `python-docx` требуют разного подхода к форматированию фрагмента, поэтому выбрать механизм после изучения фактического генератора.

## 6. Проверки
- Создание этапа с отделом; редактирование/удаление отдела; сохранение после повторного открытия модалки.
- Старые этапы без отдела, все четыре типа полей, архивные пункты.
- Версионирование и конфликт 409 при параллельной правке.
- Ответ API и разграничение компаний/ролей.
- Отображение ответственного отдела напротив каждого пункта без нарушения редактирования дат и состояний.
- DOCX: надпись появляется в конце нужного пункта; курсив применяется только к приписке; без отдела скобок нет; плановые даты не изменены.
- SVG: все действия остались работоспособными, доступны с клавиатуры и понятны скринридеру.

## Критерии готовности
Ответственный отдел сохраняется с каждым пунктом структуры; виден напротив пункта в плане; корректно передаётся API; в DOCX сразу после названия пункта появляется курсивная приписка `(отв 3 отдел)`; интерфейс настройки пользуется SVG-кнопками без потери функций и доступности; существующие планы и экспорт не ломаются.

## Важное ограничение
В текущем проверенном `main` отсутствует подтверждённая реализация DOCX-выгрузки onboarding. До выполнения части 5 необходимо установить актуальную ветку/коммит, содержащую эту фичу, и интегрироваться именно с ней.
